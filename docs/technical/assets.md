# Asset pipeline

- Blender (via Blender MCP) → export glTF (`.glb`) → `assets/` in Godot.
- `.blend` source files are committed too (open source).
- Binary assets (`.blend`, textures, audio) via **Git LFS** (watch GitHub LFS storage/bandwidth quotas).
- **Swappable models:** a gameplay scene keeps its look under a `Model` child, and its script finds the parts it animates by name among all descendants, so a modeled `.glb` can replace the greybox without code changes. The miner's model provides `Fill` (scaled along Y from 0 to 1 with the fill level, origin at its bottom), `FullLamp`, `HoseOutlet` and meshes named `Frame*`; damage (rust, hit flash, alarm blink) is drawn as an overlay on the `Frame*` meshes, so it works on top of the model's own materials. Blender models are Z-up meters; the glTF export converts to Godot's Y-up.
- **Model kits:** one `.glb` can hold many parts that scenes and resources pick by node name, e.g. all rock variants in `assets/rocks/rocks.glb`. `ModelParts` (`game/models/model_parts.gd`) reads a part's mesh (and transform) from the imported scene without instancing it. A `ScatterType` takes its mesh from `model` + `model_part`; an `OreType` names its `variants` in `model` (each a node with a `Base*` rock mesh and `Crystal*` meshes, drawn in the ore's glowing material), and each `OreNode` shows one of them. Ore badge icons (`assets/ores/icons/<ore>.png`, 256 px) need mipmaps so they stay clean at card size: set `mipmaps/generate=true` in each icon's `.import` (Godot has no per-folder import defaults; `tests/ores/test_ore_glow.gd` checks every ore's icon).
- **Ore kits:** one model kit per ore (`assets/ores/<ore>.glb`, its `.blend` in `assets/ores/source/`), so ores are added and re-baked one at a time. `assets/ores/source/ores_build.py` builds them; each ore is a module `assets/ores/source/ore_types/<ore>.py` with an `ORE = OreSpec(...)` (`ore_geo.py`: its crystal shape function, how the crystals group, preview color, the variants "a", "b" and "wall", optional `dark_body` and `smooth`), so several people (or agents) can work on different ores in parallel without touching the build script. `ores_build.py wip <tag> [ores] [views]` renders previews (the view `types` puts the "a" variants side by side), `final <ore>` saves the procedural `.blend` that `ores_bake.py <ore>` bakes into a 512 atlas, `icon <ores|all>` renders the badge icons (the main crystal group of the "a" variant, without the loose chips). The kits' textures are imported VRAM compressed (the normal map as a normal map, roughness from it), like the other models. A new ore needs its type module, a bake, its icon, its `OreType` resource and an entry in `all_ores.tres`.
- **Model files:** the game imports the `.glb` (e.g. `assets/miners/miner_glow.glb`; Godot extracts its embedded textures next to it). The `.blend` sources live in a `source/` folder with a `.gdignore` next to it, because Godot would import `.blend` files too (through Blender) and duplicate the model. Procedural Blender materials are baked into one texture set per model (base color, ORM, normal) before export. Godot doesn't import glTF transmission, so glass gets a Godot material override in the scene (see `game/mining/miner.tscn`).
- **Terrain textures:** the generated ground is drawn with `assets/shaders/terrain.gdshader`, one `ShaderMaterial` per biome (`assets/terrain/<biome>_terrain.tres`, set as the biome's `ground_material`) with three tileable texture sets: ground (6 m tile) and scree (4 m), projected from above, and rock (8 m), projected from the sides with the image's up as the world's up. Hex tiling hides the tiling: every pixel mixes three samples from randomly shifted copies of the texture on a grid of hexagons (ground and scree turned too, rock only shifted sideways so its strata stay level; `hex_cells`, `hex_contrast`), and a large noise varies the brightness (`macro_strength`, `macro_size`). Layers without weight at a pixel aren't sampled, so open ground costs 6 texture reads, cliffs 12. Rock takes over by the slope; scree comes from the vertex color's alpha, which `GeneratedLocation` paints at the foot of steep ground (higher ground within 2 grid points, `LocationTerrain.highest_around`) and in patches; the vertex color's RGB tints the low ground darker and varies the brightness over large areas. Where layers meet, the textures' heights decide (stones and ledges poke through). Each set is two 1024 px PNGs: `<layer>_albedo` (RGB base color, A height) and `<layer>_nra` (RG normal X/Y, B roughness, A AO), imported VRAM compressed in high quality (BPTC) without alpha border fix. They're made by `assets/terrain/source/terrain_textures.py` (`tools/blender.sh assets/terrain/source/terrain_textures.py [layer ...] [preview]`): each layer is real geometry (a displaced ground grid, stones, roots) with procedural materials, surrounded by eight instances of itself so everything tiles, rendered from straight above with an orthographic camera as emission passes (base color, roughness, normal, height, AO); the shader noise is periodic 4D noise on a torus, the numpy maps are filtered noise and wrapped Voronoi cells. `preview` also renders a lit 2×2 tile check to `tmp/terrain/`. Only the script and the PNGs are committed (no `.blend`, the script rebuilds the scenes in about 10 s each; reruns give the same layers, the PNG bytes differ slightly from GPU sampling).
- **Concept images:** made with Z-Image Turbo on a local ComfyUI (models listed in `tools/concepts/gen.py`; env var `COMFYUI_URL`, default `http://127.0.0.1:8188`). A batch is a prompt module in `tools/concepts/batches/` (`GROUPS`: styles x subjects with a seed base; tracked, so every batch can be rendered again); `python tools/concepts/batch.py <batch> [subject ...]` renders it into `local/concepts/<batch>/<subject>/NN_<style>.png` and records each image's prompt and seed. `python tools/concepts/rate.py` serves the rating page on port 8190: stars and a note per image, a note per subject, duels (pick the better of two) to rank the images tied at the top, a Best view with each subject's top image, filters, a Fit size that puts all images of a subject on one screen, a full-size viewer and keyboard rating (`?` lists the keys). A batch's optional `LABELS` (`{subject: text}`, e.g. a person's role) show beside the subject's name on the page. Images and ratings stay out of git: they live in `local/concepts/`, the ratings in the SQLite database `local/concepts/concepts.db`. `tools/concepts/sheet.py` makes a contact sheet of a batch's best images (needs Pillow, e.g. ComfyUI's bundled Python). The kept references and what to take from them: `local/art-references/` (its `INDEX.md`).
- **Generated models (image to 3D):** `tools/trellis.py <image> <out.glb> [--seed --faces --texture]` runs TRELLIS.2 on a local ComfyUI (0.34 or newer, its native nodes; the models it needs are listed in the script): background removal (BiRefNet), shape and texture, remeshed, decimated to `--faces` and baked into one textured `.glb` (base color, metallic/roughness, normal, AO), about 4 minutes on a 16 GB GPU, which it uses fully (run one at a time). The input is a concept image made for it: one character, front view, a relaxed A-pose with the arms clear of the body, empty open hands, no weapon or anything strapped on (fused parts can't be rigged apart; weapons are their own models). The raw output and its input are sources: `assets/<asset>/source/trellis/` holds the concept image, the generated `.glb` and `trellis.json` (what made them: models with their licenses, prompt, seeds, settings, date); the build script fits and rigs it (see Characters) with the shared helpers in `tools/blender/generated.py` (loading and welding the raw mesh, the nearest-bone weights with blends across the joints, cutting the faces between parts that move apart, reading and repainting its texture). Generated so far: the player's suit, the swarmer, Nell's outfit and hair, Kade's, Selin's, Rook's and the crew's outfits and heads. Licenses: TRELLIS.2 and BiRefNet are MIT, Z-Image Turbo (the concept images) Apache-2.0; DINOv3 (TRELLIS.2's image encoder) has its own license, which doesn't address outputs (we don't ship its weights, so its "Built with DINOv3" notice doesn't apply). Every generated asset counts as pre-generated AI content for Steam's disclosure (see the checklist in [`platform.md`](platform.md#steam-publishing-first-timer-checklist)).
- **Generated images:** the emblem (`assets/ui/boot/emblem.png`) is a Z-Image Turbo concept (`tools/concepts/`, batch 9: emblem ideas and wordmarks; the wordmarks misspelled the name, so the name is set in the game's font beside the emblem), cut out by `assets/ui/boot/source/emblem_build.py`; `source/` keeps the concept and `emblem.json` (what made it, like `trellis.json`).
- **Asset scripts:** a modeled asset is built by Python scripts next to its `.blend` (e.g. `assets/miners/source/miner_glow_build.py` models it with procedural materials, `miner_glow_bake.py` bakes the textures and writes the `.blend` and `.glb`), with shared helpers in `tools/blender/`: `common.py` for building (transforms, the `Part` mesh builder, material node helpers, preview scene, renders, contact sheets, export) and `bake.py` for the bake. A bake script only describes its asset in a `bake.Job` (objects sharing the atlas, texture size and supersampling, material name, optional hooks for bake-only props, a custom unwrap or constant materials) and calls `bake.run()`: unwrap into one atlas, bake base color / ORM / normal (and emission), fill the gaps between the islands, swap in one baked PBR material, export, re-import and render checks. It bakes without Blender's bake margin (with several objects, one object's margin paints over the others' islands) and grows the islands itself. `<script> verify` only re-imports and renders the checks (the player's `player_bake.py clips` takes clips the build added since the last bake into the baked `.blend` and re-exports, without baking the textures again); the env var `BAKE_OUT=<dir>` writes the `.glb`, `.blend`, textures and checks to `<dir>` instead, to compare a re-bake without touching `assets/`. Run them headless with `tools/blender.sh <script> [args]`, which needs the env var `BLENDER` (path to the Blender executable). Preview renders and intermediate files go to `tmp/`; only the scripts, the baked `.blend` and the `.glb` are committed.
