# Engine settings

- **Versions:** each version is defined once and referenced everywhere else. Godot: `.godot-version` (read by CI and scripts; when upgrading, also let the editor update `config/features` in `project.godot`). godot-ai: `.mcp.json`, kept equal to `addons/godot_ai/plugin.cfg`.
- Renderer Forward+, Jolt physics, **Vulkan on all platforms** (Godot's default, so `project.godot` has no driver line). D3D12 was rejected: in a sibling project on the same Godot 4.7.2 + SteamVR setup it logged texture errors every frame and the headset image stayed black, while Vulkan worked. Retry D3D12 only after a Godot update and with a reason.
- **Performance targets** (see [`design/overview.md`](../design/overview.md#platform-and-technical-constraints)): desktop 60 FPS minimum, 120–144 target; VR 90 minimum, with two views per frame. Settings follow from that:
  - Display: base resolution 1920×1080 (the reference size for 2D and stretching; 3D renders at the window's native resolution), fullscreen (borderless) by default, also when run from the editor. Window mode and resolution become player settings later.
  - Anti-aliasing: MSAA 2x for 3D (sharp geometry edges, works in VR), no TAA/FXAA (blur and smearing, worst in VR). The level is a starting value, **TBD (playtest)**, later a player setting.
  - Physics interpolation on: physics ticks at 60 Hz while the display runs at 90–144 Hz, interpolation keeps movement smooth without raising the tick rate. Nodes that are moved outside `_physics_process` or teleported need `reset_physics_interpolation()`.
  - Expensive per-`Environment` effects (SDFGI, SSR, volumetric fog) are off by default and only added when a profile shows the budget for them; the art direction leans on rim light and emissive accents for readability instead.
  - Look of the outside (`game/maps/main.tscn`): AgX tonemapping, glow (bloom) only above HDR 1.2, so only emissive parts bloom (ore, eyes, lamps), a dim warm sun, a faint cool back light without shadows and low ambient light. Aboard, `Weather` raises the ambient light (`indoor_ambient_energy`), because the cut-away roof still shades the rooms. Values are **TBD (playtest)**.
  - Rim light: `assets/shaders/rim_light.tres` is a material overlay that adds a cool glow along the outline, independent of the lights (players, aliens, miners). It costs one extra additive pass per mesh that uses it.
  - Ore glow: `OreType.get_material()` (crystals, `assets/shaders/ore_crystal.gdshader`) and `get_glow_material()` (miner column, hose, canisters, `ore_fill.gdshader`) are `ShaderMaterial`s made by `OreGlow` (`game/ores/ore_glow.gd`), shared per ore type, with the ore's `color`, `glow` (the `OreType.Glow` index) and `dark_body` as uniforms; full brightness is emission energy 2.5. Both include `ore_glow_spatial.gdshaderinc` (the crystal shader defines `ORE_CRYSTAL`), and all ore shaders take the rhythms from `ore_glow.gdshaderinc`, which `OreGlow.intensity(glow, time, phase)` repeats in GDScript (change both together; `tests/ores/test_ore_glow.gd` checks the range and that no pattern peaks more than 3 times a second). Flicker is smooth value noise (3.5 steps per second) times a slow noise for dips; wave bands use the mesh's height (object space; for the hose, world height); sparkle hashes each flat-shaded facet's normal to glint at its own time (fill materials only shimmer); breathing brightens the faces towards the camera (a fresnel core); shifting turns the hue around the grey axis, on crystals also by the viewing angle. A dark body is near-black and glossy, with emission only along the edges of 3D cells in object space (`vein_density` per meter, at least about a pixel wide via `fwidth`) and a faint rim; filled things glow dimly between the veins. Each instance gets its own `phase` (an `instance uniform`, `OreGlow.set_phase`, from `OreGlow.phase_at(position)`, set by `OreNode` and `Miner`, so a miner pulses with its deposit); without one the shader takes it from the node's position.
  - Occlusion culling is still off. The ship's shell (M5) could be baked as occluders now: worth a profile with M6's 90 FPS work; enable it on SubViewports too.
  - Renderer for VR: Forward+ is used for PC VR. Whether Steam Frame standalone needs the Mobile renderer is checked in M6, through a feature override (see above), not by switching the default.
- **Input map** (`[input]` in `project.godot`, checked by `tests/project/test_input_map.gd`): every gameplay action has a keyboard/mouse and a gamepad binding on all devices (developer tools only get a key); keys use physical keycodes so WASD stays in place on non-QWERTY layouts. Mouse aiming uses the cursor position, so `aim_*` only has right-stick bindings. godot-ai can only bind logical keycodes: add keys with the editor closed or via the editor's Input Map tab ("Physical Keycode"). Stick deadzone 0.2 is a starting value, **TBD (playtest)**.

- **Navigation:** 0.5 m cells (`navigation/3d/default_cell_size`; navigation meshes must use the same), so baking the generated outside world stays under a second; `merge_rasterizer_cell_scale` is 0.01, which avoids most edge merge errors on its terrain; the few left on some worlds (a handful of unlinked edges among about 12,000 polygons) are harmless, so their warning is off (`navigation/3d/warnings/navmesh_edge_merge_errors`). The map takes a baked mesh over in the background, so paths exist a few frames after the bake. The generated world bakes on its own `WorkerThreadPool` task (`LocationNavigation`), not with `bake_from_source_geometry_data_async`: a region freed mid-bake waits for the task, since quitting while a bake still runs crashes the engine on exit (the async bake can't be waited for, its end is only noticed on the main thread). Aliens search the whole navigation mesh for a path (`path_search_max_polygons = 0` on their agent): around the rock of a generated location, the default limit (4096 polygons) ran out on long ways around, and Godot's fallback search then logged "It's not expect to not find the most reachable polygons" every frame. **Queries are expensive:** Godot 4.7 finds the polygon closest to a point by going through every polygon of every region, so `map_get_closest_point` takes about 0.35 ms and a path look-up (both ends) about 0.5 ms on a generated world (10,000–15,000 polygons), short ways too; baking the world in tiles (one region each) didn't help. So aliens look a path up again only once its end moved 1 m or a fifth of the way, at most two per physics frame (`AlienPathing`), and nothing calls `map_get_closest_point` per frame (burrowers follow the ground with a short ray, backing off holds its spot for half a second).
- **Many aliens** (M4 step 9 A, measured in a late, frenzied tier 6 run with the cap full and the player running): each alien costs about 100–150 µs a frame on screen (leg IK, its `AnimationTree`, skinning and drawing) and its AI, `move_and_slide` and avoidance on top while it moves. A `VisibleOnScreenNotifier3D` (its body's box, grown by 1.5 m for shadows and legs) switches off an alien's `AlienLegs` (`culled`), `AnimationTree` and `_process` (pose, glow) off screen, except the Ravager's (its steps shake the ground); headless nothing is on screen, so `Alien.culls_off_screen` is off there (tests). An alien standing on the ground skips `move_and_slide`, its material is only touched on a change, and fliers push apart only from fliers (`AlienFlight.GROUP`). Setting an alien up costs about 1 ms (the first stalker or tender of a session 12–20 ms), so nests hatch from a queue: one alien per pack every `hatch_gap`, the hive at most one per physics frame; nests at the cap look again every `CAP_RETRY` instead of every tick. Watch out when measuring on Windows: tools polling the GPU driver (e.g. an `nvidia-smi` based exporter) cause 30–50 ms hitches every few seconds, even in an empty scene.
- **Physics layers:** everything collides on layer 1. Layer 2 only stops projectiles (they raycast against every layer; players and aliens only collide with layer 1), e.g. the force field in the ship's shooting range doorway.
- **Location viewer** (`game/debug/location_viewer.tscn`, 2D, developer only): plans generated locations (with the game's isometric view, V toggles it; the white arrow shows where the camera looks) and draws them from above: walkable ground light (darker the lower it lies, with terraces), the barrier brown where it's rock and in the biome's gap tint where it's a gap (white lines for the walls along a gap's edge), bridges lighter, trails' paths darker, buttes as rings, a dry wash's bed as a sandy line, terrace stairs' slabs as squares with their ramps, the hazard in its tint with a ring and its name, the passes, the areas with their kind and walking distance, ore nodes in their ore's colors (a rich field's bigger), nests, the lanes kept free, the map parts in amber (footprint, props, name, a set piece's in capitals, crates as squares, quest sites as diamonds), and in magenta any spot a player could fall to without a way back (should be none). Left/Right change the seed, Up/Down the number of areas, B the biome, G the region (its biome and set pieces), R a random seed, S saves a picture to `user://location_viewer/`. Run it from the editor (F6 on the scene), or for one picture: `"$GODOT4_EDITOR" --path . game/debug/location_viewer.tscn -- --seed=3 --areas=11 --biome=0 --region=0 --view=1 --shot=tmp/layout.png` (`--region`: index into the star system's regions, -1 none).
- **Palette viewer** (`game/debug/palette_viewer.tscn`, 2D, developer only): every color the game uses as tiles in groups (players, ores, the hive, silhouettes, health, ammo, the suit ring, the ship's status, the mission, menus, danger, skill clusters, biomes and bodies on the map, the crew), read from where the game keeps them (the resources, the classes' constants, the weapon scenes' ammo gauges), so new ores, weapons or crew show up by themselves; a color kept somewhere else needs a line in `PaletteViewer.groups()`. Alpha and glow are left out. `ColorVision` simulates the three common color blindnesses (protanopia, deuteranopia, tritanopia at full strength, Machado et al. 2009, in linear RGB) and measures how far apart two colors look (OKLab distance). 0 shows all four visions side by side, 1–4 one of them with the names and the pairs that look closest (under 0.08, **TBD (playtest)**): colors of one group, or of two groups seen together during a run, that look nearly the same with that vision; with a color blindness only the pairs that look apart normally (what it loses), and colors used twice on purpose (under 0.02 normally) are left out. Ores also differ by crystal shape and glow, players by their number, so a close pair there is a hint. The mouse over a tile names it with its hex values, S saves a picture to `user://palette_viewer/`. Check new colors here against the ones they're seen with before using them (run it when colors change; it's not a CI check): from the editor (F6 on the scene), or for one picture `"$GODOT4_EDITOR" --path . game/debug/palette_viewer.tscn -- --vision=2 --shot=tmp/palette.png` (`--vision`: 0 all four, 1 normal, 2–4 the color blindnesses).
- **Debug overlay** (autoload `DebugOverlay`, `game/debug/debug_overlay.gd`): a 2D developer panel, toggled with F3, in English, with two tabs: "State" (the live values and the shortcuts, grouped) and "Tuning" (a folded section of sliders per settings resource). It only exists when the game runs from the editor (`OS.has_feature("editor")`, also true for the headless tests); exported builds, debug ones included, remove it at start. It shows the mission state, the ship's flight phase, time, escalation, player health, how many aliens are left (chasing, hunters, raiders), how many nests there are (and destroyed) and how many miners (broken), has shortcuts (skip to the warning time, storm now, skip the flight, kill / heal players, kill aliens, let every nest hatch a hunter or a raider, take a burst's share of health off every nest (each press one stage), break every miner, unlock every weapon for every player, fill the hold with 900 units of every ore to test the upgrade stations, give ore, add teammates that stand still and remove them, reset the save and reload the map), switches for god mode (players lose no health, hits still flash the suit light and mark the ring; kill players still kills) and the aliens' AI (off: every alien stands where it is without a target or an attack, burrowers come up, they can still be hit and killed; nests keep hatching) and sliders for the settings resources (`TUNING` in the script; add new tuning values there; integer settings get whole-number sliders). Sliders change the loaded resources live, so every scene using them sees the new value; changes last until the game stops and aren't saved, so copy good values into the `.tres` files by hand. A tuned mission duration also moves the running timer. While the mouse is over the panel, the player neither aims nor attacks with it.
- **User data, logs and crashes:** `application/config/use_custom_user_dir` gives the game its own user data folder (`user://`) named after it, instead of Godot's `app_userdata/<name>`: `%APPDATA%\Lodestorm` on Windows, `~/.local/share/Lodestorm` on Linux (or under `$XDG_DATA_HOME`), `~/Library/Application Support/Lodestorm` on macOS; runs from the editor use it too. Godot's file logging (on by default on desktop, release builds too) writes each run to `logs/godot.log` there; the next start renames it to `godot<date>.log`, and the last 5 are kept. There's no crash dump: on a crash Godot's crash handler logs the engine version and a native backtrace (without symbols in release builds: addresses only), and `debug/settings/gdscript/always_track_call_stacks` adds the GDScript call stack to errors and crashes in release builds too (at a small cost per call). A crash inside the GPU driver can end the process before the handler runs; then the log just stops. Players reach the folder with "Open folder" in the settings (`SettingsList.logs_folder`), and the bug report template (`.github/ISSUE_TEMPLATE/bug_report.yml`) asks for the newest log files and names the folder per system.
