## 2. Code quality

| Tool | Purpose |
|---|---|
| [godot-gdscript-toolkit](https://github.com/Scony/godot-gdscript-toolkit) `gdlint` | Linting (naming, complexity, ordering) — config in `gdlintrc` (only overrides of the defaults) |
| `gdformat` (same toolkit) | Formatting, checked with `gdformat --check` — config in `gdformatrc` |
| Godot GDScript warnings | **Every warning is an error** in the project settings (`debug/gdscript/warnings/*`), so a script with one fails to load and `tests/project/test_scripts_parse.gd` fails in CI: the default warnings (shadowing, integer division, unused variables, ...) and the typing ones Godot ignores by default (`untyped_declaration`, `unsafe_property_access`, `unsafe_method_access`, `unsafe_call_argument`). Where integer division is meant, say so with `@warning_ignore("integer_division")`. `addons/` is exempt (Godot's default `directory_rules`) |
| Unit tests | [GUT](https://github.com/bitwes/Gut) in `addons/gut/` (version in its `plugin.cfg`, must support the pinned Godot version), tests in `tests/` (`test_*.gd`, config `.gutconfig.json`), run headless |
| [ruff](https://docs.astral.sh/ruff/) | Formatting and linting of the Python scripts (Blender asset scripts, `tools/blender/`) — config in `ruff.toml` (ruff's default rules, only overrides; line length 120 because the asset scripts are full of coordinate tables; target: Blender's bundled Python) |
| `.editorconfig` | Consistent whitespace/line endings across editors |

All checks are enforced by CI on every pull request (failing jobs block the merge), not by local git hooks. The same scripts run locally and in CI:

- `tools/lint.sh` — `gdformat --check` + `gdlint` over the project (`addons/`, `local/`, `tmp/` excluded in the rc files), then `ruff format --check` + `ruff check` (ruff skips what git ignores, and `addons/`) and whether the generated ship hull matches its generator (`game/ship/hull_build.py --check`); `tools/lint.sh gdscript` or `tools/lint.sh python` runs only one half. gdtoolkit and ruff are pinned in `requirements-dev.txt`: `pip install -r requirements-dev.txt`, ideally in a `.venv/` (gitignored).
- `tools/test.sh` — imports the project (`tools/import.sh`: fails if the import prints any `ERROR`, e.g. an LFS pointer instead of a file), then runs GUT headless with `$GODOT4_EDITOR`, split round-robin over `TEST_JOBS` parallel processes (default 4; each one's output is printed when all are done). Extra arguments go to GUT in a single process instead (e.g. `-gselect=test_foo.gd`). Exits non-zero on failures.
- Tests run with `--fixed-fps 60` (the physics tick rate): every frame advances exactly one physics tick and simulated time doesn't wait for the wall clock, so `wait_seconds` / `wait_physics_frames` only take as long as computing the frames. Anything that runs in real time (worker threads like location planning, the background bake of the walkable area) must be waited for with `tests/support/real_time.gd` (`await REAL_TIME.wait_until(condition, seconds)`, a wall-clock timeout; assert its result), not GUT's `wait_until`, whose seconds are simulated and run out long before a busy CI runner finishes the work. Wait for the real end state (e.g. the navigation map synced with the baked region, which also can't be queried before its first sync), not for a side effect.
- GUT silently skips test scripts that fail to parse, so `tests/project/test_scripts_parse.gd` loads every project script and fails on parse or typing errors.
- `tools/uids.sh` (`tools/uids.gd`, headless) gives every scene and resource its own UID and every `ext_resource` the UID of its target, as the editor writes them, so references survive moving files; a copied file gets a new UID. Run it after writing or patching `.tscn`/`.tres` files without the editor; `tests/project/test_resource_uids.gd` fails until then.
- Tests that need the map get it from `tests/support/test_map.gd`: the main map with the small hand-built test location instead of the generated outside world (fixed ore nodes, rocks and nests; generating a location takes about a second per test). The ramp button needs a picked mission: `pick_mission(map)` picks the first one on offer (picking reinstances the location).

### Project layout

The game lives in `game/`, one folder per feature: its scenes, scripts and resources together, so a feature is found (and moved, or worked on in parallel) in one place. Imported art stays in `assets/` (the Blender pipeline writes there), tests in `tests/`, mirroring `game/`.

Rules: a folder is named after a game concept, never `utils`/`common`/`core` (a shared helper goes to the feature it serves, or gets its own named folder like `models/`). A scene's tuning `.tres` sits next to it (e.g. `game/player/player_settings.tres`); a feature's content (one resource per ore, weapon, skill, ...) goes in a subfolder (`types/`, `tree/`, `crew/`). Later features (VR, co-op, platform services) get their own folders (`vr/`, `net/`, `platform/`). Developer shell scripts live in `tools/` (ignored by Godot via `.gdignore`).

**The ship** (`game/ship/ship.tscn`) is put together from parts, so the hull and each room can be changed (and later modeled) on their own:

- `hull.tscn`: the greybox hull (floors, walls with doors and windows, the upper deck's slab, roof, nose cone, landing gear, thrusters), generated by `game/ship/hull_build.py` (`python game/ship/hull_build.py`). Don't edit it by hand; the art pass replaces it with the modeled hull.
- `rooms/` (`lower/`, `upper/`, `cargo_bay.tscn`): a scene per room with its floor, light, sign, props, stations and NPCs, edited by hand. `ship.tscn` places each at its floor center under `Rooms/Lower`, `Rooms/Upper` or `Rooms`, so node paths like `Rooms/Lower/Armory/Locker1` stay the same.
- `materials/`: materials used by more than one of these scenes (props, beds, lockers, floor guides).
- `ship.tscn` itself keeps what belongs to the whole ship: the lifts, the floor guides between rooms, the ramp and its button, the boarding and respawn markers, the hold, the countdown and the flight.

The layout (each room's position and size) is defined in `hull_build.py`: moving or resizing a room means changing it there, rebuilding the hull, and moving the room's scene (and resizing its floor) to match.

### Conventions

- Static typing everywhere (`var speed: float = 5.0`, typed function signatures).
- Follow the official GDScript style guide (snake_case files/functions, PascalCase classes/nodes).
- Gameplay logic separated from presentation where it helps testing (e.g. miner fill logic, resource inventory, upgrade math as plain testable classes/resources).
- Tunable values live in `Resource` files (`.tres`), not hardcoded — needed for playtest tuning anyway.

### Cross-platform development

Development must work on Windows (Git Bash), Linux and macOS.

- Scripts are POSIX `sh`/`bash` (no PowerShell/`.bat`-only tooling); avoid GNU-only flags (e.g. `sed -i` differs on macOS) or use Python instead.
- No hardcoded absolute or machine-specific paths; use env vars (`GODOT4_EDITOR`, `BLENDER`, `BLENDER_MCP_PATH`) and paths relative to the repo root.
- Line endings are LF (`.gitattributes`); mark scripts executable in git with `git update-index --chmod=+x` (Windows doesn't keep the bit).
- File names: lowercase, no spaces, never rely on case to distinguish files (Windows/macOS file systems are case-insensitive).
- Platform-specific project settings use Godot feature overrides (e.g. `rendering_device/driver.windows`), never replace the shared default.

### Engine settings

- **Versions:** each version is defined once and referenced everywhere else. Godot: `.godot-version` (read by CI and scripts; when upgrading, also let the editor update `config/features` in `project.godot`). godot-ai: `.mcp.json`, kept equal to `addons/godot_ai/plugin.cfg`.
- Renderer Forward+, Jolt physics, **Vulkan on all platforms** (Godot's default, so `project.godot` has no driver line). D3D12 was rejected: in a sibling project on the same Godot 4.7.2 + SteamVR setup it logged texture errors every frame and the headset image stayed black, while Vulkan worked. Retry D3D12 only after a Godot update and with a reason.
- **Performance targets** (see [`GAME_DESIGN.md`](GAME_DESIGN.md#2-platform--technical-constraints)): desktop 60 FPS minimum, 120–144 target; VR 90 minimum, with two views per frame. Settings follow from that:
  - Display: base resolution 1920×1080 (the reference size for 2D and stretching; 3D renders at the window's native resolution), fullscreen (borderless) by default, also when run from the editor. Window mode and resolution become player settings later.
  - Anti-aliasing: MSAA 2x for 3D (sharp geometry edges, works in VR), no TAA/FXAA (blur and smearing, worst in VR). The level is a starting value, **TBD (playtest)**, later a player setting.
  - Physics interpolation on: physics ticks at 60 Hz while the display runs at 90–144 Hz, interpolation keeps movement smooth without raising the tick rate. Nodes that are moved outside `_physics_process` or teleported need `reset_physics_interpolation()`.
  - Expensive per-`Environment` effects (SDFGI, SSR, volumetric fog) are off by default and only added when a profile shows the budget for them; the art direction leans on rim light and emissive accents for readability instead.
  - Look of the outside (`game/maps/main.tscn`): AgX tonemapping, glow (bloom) only above HDR 1.2, so only emissive parts bloom (ore, eyes, lamps), a dim warm sun, a faint cool back light without shadows and low ambient light. Aboard, `Weather` raises the ambient light (`indoor_ambient_energy`), because the cut-away roof still shades the rooms. Values are **TBD (playtest)**.
  - Rim light: `assets/shaders/rim_light.tres` is a material overlay that adds a cool glow along the outline, independent of the lights (players, aliens, miners). It costs one extra additive pass per mesh that uses it.
  - Ore glow: `OreType.get_material()` (crystals, `assets/shaders/ore_crystal.gdshader`) and `get_glow_material()` (miner column, hose, canisters, `ore_fill.gdshader`) are `ShaderMaterial`s made by `OreGlow` (`game/ores/ore_glow.gd`), shared per ore type, with the ore's `color`, `glow` (the `OreType.Glow` index) and `dark_body` as uniforms; full brightness is emission energy 2.5. Both include `ore_glow_spatial.gdshaderinc` (the crystal shader defines `ORE_CRYSTAL`), and all ore shaders take the rhythms from `ore_glow.gdshaderinc`, which `OreGlow.intensity(glow, time, phase)` repeats in GDScript (change both together; `tests/ores/test_ore_glow.gd` checks the range and that no pattern peaks more than 3 times a second). Flicker is smooth value noise (3.5 steps per second) times a slow noise for dips; wave bands use the mesh's height (object space; for the hose, world height); sparkle hashes each flat-shaded facet's normal to glint at its own time (fill materials only shimmer); breathing brightens the faces towards the camera (a fresnel core); shifting turns the hue around the grey axis, on crystals also by the viewing angle. A dark body is near-black and glossy, with emission only along the edges of 3D cells in object space (`vein_density` per meter, at least about a pixel wide via `fwidth`) and a faint rim; filled things glow dimly between the veins. Each instance gets its own `phase` (an `instance uniform`, `OreGlow.set_phase`, from `OreGlow.phase_at(position)`, set by `OreNode` and `Miner`, so a miner pulses with its deposit); without one the shader takes it from the node's position.
  - Occlusion culling stays off until there are occluders to bake (ship interior, M3); remember to enable it on SubViewports too.
  - Renderer for VR: Forward+ is used for PC VR. Whether Steam Frame standalone needs the Mobile renderer is checked in M6, through a feature override (see above), not by switching the default.
- **Input map** (`[input]` in `project.godot`, checked by `tests/project/test_input_map.gd`): every gameplay action has a keyboard/mouse and a gamepad binding on all devices (developer tools only get a key); keys use physical keycodes so WASD stays in place on non-QWERTY layouts. Mouse aiming uses the cursor position, so `aim_*` only has right-stick bindings. godot-ai can only bind logical keycodes: add keys with the editor closed or via the editor's Input Map tab ("Physical Keycode"). Stick deadzone 0.2 is a starting value, **TBD (playtest)**.

  | Action | Keyboard / mouse | Gamepad (Xbox / PlayStation) |
  |---|---|---|
  | `move_left/right/forward/back` | WASD | left stick |
  | `aim_left/right/forward/back` | cursor | right stick |
  | `attack` | left mouse button | RT / R2 |
  | `interact` | E | A / Cross |
  | `place_miner` | F | X / Square |
  | `switch_weapon` | Q | Y / Triangle |
  | `reload` | R | RB / R1 |
  | `pause` | Escape | Menu / Options |
  | `debug_overlay` | F3 | — |

- **Navigation:** 0.5 m cells (`navigation/3d/default_cell_size`; navigation meshes must use the same), so baking the generated outside world stays under a second; `merge_rasterizer_cell_scale` is 0.01, which avoids most edge merge errors on its terrain; the few left on some worlds (a handful of unlinked edges among about 12,000 polygons) are harmless, so their warning is off (`navigation/3d/warnings/navmesh_edge_merge_errors`). The map takes a baked mesh over in the background, so paths exist a few frames after the bake. Aliens search the whole navigation mesh for a path (`path_search_max_polygons = 0` on their agent): around the rock of a generated location, the default limit (4096 polygons) ran out on long ways around, and Godot's fallback search then logged "It's not expect to not find the most reachable polygons" every frame.
- **Physics layers:** everything collides on layer 1. Layer 2 only stops projectiles (they raycast against every layer; players and aliens only collide with layer 1), e.g. the force field in the ship's shooting range doorway.
- **Location viewer** (`game/debug/location_viewer.tscn`, 2D, developer only): plans generated locations and draws them from above: walkable ground light, the rock dark, the passes, the areas with their kind and walking distance, ore nodes in their ore's colors, nests, the lanes kept free, and in magenta any spot a player could fall to without a way back (should be none). Left/Right change the seed, Up/Down the number of areas, B the biome, R a random seed, S saves a picture to `user://location_viewer/`. Run it from the editor (F6 on the scene), or for one picture: `"$GODOT4_EDITOR" --path . game/debug/location_viewer.tscn -- --seed=3 --areas=11 --biome=0 --shot=tmp/layout.png`.
- **Debug overlay** (autoload `DebugOverlay`, `game/debug/debug_overlay.gd`): a 2D developer panel, toggled with F3. It only exists when the game runs from the editor (`OS.has_feature("editor")`, also true for the headless tests); exported builds, debug ones included, remove it at start. It shows the mission state, the ship's flight phase, time, escalation, player health, how many aliens are left (chasing, hunters, raiders), how many nests there are and how many miners (broken), has shortcuts (skip to the warning time, storm now, skip the flight, kill / heal players, kill aliens, let every nest hatch a hunter or a raider, break every miner, unlock every weapon for every player, fill the hold with 900 units of every ore to test the upgrade stations, reset the save and reload the map) and sliders for the settings resources (`TUNING` in the script; add new tuning values there; integer settings get whole-number sliders). Sliders change the loaded resources live, so every scene using them sees the new value; changes last until the game stops and aren't saved, so copy good values into the `.tres` files by hand. A tuned mission duration also moves the running timer. While the mouse is over the panel, the player neither aims nor attacks with it.

### Localization

English and German so far (see [`GAME_DESIGN.md`](GAME_DESIGN.md#localization-and-voice)), with gettext PO files in `locale/`: one file per language, plain text, readable in a diff.

- **Texts are the English originals:** a scene's text property (e.g. `Label3D.text`) or `tr("Text")` in a script is the key, and English needs no translation file. Write them in sentence case ("Mess hall"); labels that show capitals set `uppercase`, so translations don't have to shout. `tr("Text", "context")` tells apart texts that read the same but translate differently.
- `locale/lodestorm.pot` is the template with every text. `tools/translations.sh` (`tools/translations.gd`, headless) collects it from `game/` (text properties of nodes, unless their auto translation is disabled; `tr()` calls with string literals; the player-facing texts of resource types listed in `RESOURCE_TEXTS`, e.g. biome names, weapon names and descriptions, also of resources built into another one, like the star system's bodies and regions) and brings every translation listed in the project settings (`internationalization/locale/translations`) up to date: new texts come in untranslated, unused ones go. Run it after adding or changing texts, then fill in the translations.
- `tests/project/test_translations.gd` fails when the template or a translation is out of date, or when a listed translation misses a text, so every new text needs its German translation in the same pull request.
- Nodes translate their texts themselves, also when the language changes while playing. A label whose text is set from code (e.g. the countdowns) disables its auto translation and gets `tr()` results, so nothing is translated twice.
- The game follows the system language (regional variants like `de_AT` use `de`, unknown languages show English); the settings terminal (`SettingsMenu`) switches it while playing and saves it (`GameSettings`, see [Saving](#saving)); `--language de` on the command line forces one for testing. The tests always run in English (`tests/support/pre_run.gd`).
- Room for longer texts: German runs about a third longer than English. Floor markings (`FloorGuide`) never get wider than their English text; they wrap between rooms instead and grow away from their arrow, which stays in place.
- **Adding a language:** create `locale/<code>.po` with a header (`Language: <code>`), add it to the translations in the project settings, add the language's own name to `SettingsMenu.LANGUAGE_NAMES`, run `tools/translations.sh` and translate every entry.

### Saving

What's saved and when: [`GAME_DESIGN.md`](GAME_DESIGN.md#11-death--persistence). A `SaveGame` node in the map (`game/save/save_game.gd`) loads the save when the map starts and writes it.

- **Files:** JSON in `save/` under `SaveGame.directory`: `ship.json` for the host's part (the hold and the story's flags, `Ship.story`; later crew and quests) and `player.json` for the local player's (owned weapons, loadout, upgrade levels, skill ranks), split for co-op (see [Co-op progression](GAME_DESIGN.md#co-op-progression)). The settings are in `settings.cfg` (`ConfigFile`, `game/save/game_settings.gd`) next to `save/`, so resetting keeps them.
- **Where:** Godot's user data folder (`user://`); runs from the editor use `user://dev/`, so the debug overlay's shortcuts never reach a real save. The tests never touch either: `tests/support/pre_run.gd` sets `SaveGame.directory` to empty (nothing is loaded or saved), and `tests/save/test_save_game.gd` uses its own folder.
- **When:** on every change of the hold, the story, the arsenal, the loadout, the upgrades or the skills (`changed` / `Ship.hold_changed`, batched to one write per frame) unless a mission is underway (`Mission.is_underway`), and when a mission is returned or lost.
- **Format:** each file has a `version` (`SaveGame.VERSION`); raise it and convert older saves in `SaveGame._read` when the format changes. Newer saves aren't read. Ore types, weapon types, upgrades and skills are saved by their UID (`uid://...`), so they can be moved and renamed; version 1 saved `res://` paths, which `SaveGame.MOVED` maps to where the files are now. Entries that don't resolve to the expected resource type are skipped with a warning; weapons are never taken away and the locker never empties the loadout, so a save without a known (owned) weapon keeps the default arsenal (loadout) instead of leaving the player unarmed. A save that was older or needed repairs is written again right after loading; a file that can't be parsed is kept as `<file>.corrupt` and the game starts from the defaults. Files are written to `<file>.tmp` first and then renamed, so a crash never leaves half a save.
- **Reset:** `SaveGame.reset_progress` deletes `save/` and reloads the map, only while `SaveGame.is_solo` (no connected peers and at most one player; hosting a session alone counts, since friends can join any time); the settings terminal disables its button otherwise.
- **Language:** the saved one is applied when the map enters the tree, unless the command line forced another one (`--language`; detected as a locale other than the system's, so forcing the system language doesn't win).

### 3D menus

Menus are things in the world (see [`GAME_DESIGN.md`](GAME_DESIGN.md#ui-in-the-world-not-on-the-screen)), each a `WorldMenu` (`game/ui/world_menu.gd`): one player uses it at a time (`open`/`close`, `Player.menu`), and while they do, the camera frames it (`view_height`, `view_focus`). There are two kinds: screens (`WorldPanel`, on terminals) and stations (`Station`, the object is the menu).

**Screens:** a `WorldPanel` (`game/ui/world_panel.tscn`) renders a normal Control scene (`menu`) in a SubViewport onto an unshaded quad. A `Terminal` (`game/ui/terminal.tscn`, an `Interactable`) is a console with such a screen; set its `menu` to the Control scene. The settings terminal in cabin 1 shows `game/ui/settings_menu.tscn` (the only terminal left: system things only).

- **Ore badges:** `OreBadge` (`game/ores/ore_badge.gd`) shows an ore on a card: its `OreType.icon` (a white crystal silhouette with grey facets on transparent) through `assets/shaders/ore_badge.gdshader`, which tints the greys in the ore's color and plays its glow pattern (from `ore_glow.gdshaderinc`; sparkle per grey level, i.e. per facet; shifting turns the hue; a dark body is a dark icon with a colored rim and facet edges), and optionally its translated name. An ore without an icon gets a four-facet crystal drawn in code (`OreBadge.fallback_icon`). The navigator, flight and cost (`OreCost`) rows list ores as badges with their names in `HFlowContainer`s, so they wrap; the cards are sized for six ores with the longest names (`tests/stations/test_menu_fit.gd`).
- **Building a menu:** a Control scene filling its viewport, laid out for `size * pixels_per_meter` (960 × 600 for the default 1.2 × 0.75 m screen), with `assets/ui/terminal_theme.tres` (fonts 30 px, titles 46 px with the `Title` variation; a focus style that stands out, since gamepads navigate by focus). Texts go through translations like any scene (see Localization). A control closes its menu with `WorldPanel.showing(self).close()`.
- **Using:** `open(player)` sets `Player.menu`; the player then ignores movement, aiming and actions (an action still held when the menu opens or closes waits for its release, so the closing press doesn't act in the world). The `IsoCameraRig` moves to the menu (or its `view_focus`, e.g. a station's object and its card) and zooms until it sees `view_height` m (1.6 for a terminal, a station sets its own, **TBD (playtest)**; a `Terminal` passes both on to its panel). The screen material switches to no depth test while used and renders after the player's silhouette and rim light (`ON_TOP_PRIORITY`), so a player standing in front doesn't hide it.
- **Input:** while open, the panel takes the events in `_input`. Mouse events become a ray from the camera; `pixel_at(origin, direction)` turns it into a menu pixel, and the event is pushed into the SubViewport (`push_input(event, true)`: layout coordinates). A VR controller will use `pixel_at` the same way. Other events are translated into GUI actions (`NAVIGATION`: `move_*` and `ui_*` directions, `interact` and `ui_accept`), so the menus use Godot's focus navigation; a held stick presses once, held keys repeat. `pause` and `ui_cancel` close.
- **Sharpness:** the SubViewport keeps its layout size as `size_2d_override` (stretched) and renders at about the pixels the screen covers on the display, in half-octave steps (`_update_resolution`): zoomed in on a 4K display that's 2× the layout, from the isometric distance 1/8 (viewport textures have no mipmaps, so a big texture would shimmer). Fonts re-rasterize at that size (viewport oversampling), so text stays crisp.
- **Testing:** push input into the root viewport with `push_input(event, true)`: without it the window rescales the position (a headless window is tiny). Headless, the window is too small to test the render resolution; check it with a windowed probe.

**Stations** (`game/stations/station.gd`, each station in its own folder, e.g. `game/stations/navigator/`): an object whose parts are the menu. The scene's root is the `Station` (or a subclass); children:

- `Use`: an `Interactable` (with an optional `Highlight`) that opens it; disabled while used.
- `user_spot`: a marker where the player using it stands, looking along its -Z (beside the object, so they don't hide it); `view_focus` and `view_height` frame the object and the card.
- `StationPart`s (`game/stations/station_part.gd`): the selectable parts. `item` is what the part stands for (an `Upgrade` at an upgrade station), `pick_radius` how close the mouse cursor must be (screen distance to its center), `card_offset` where the card floats (right/up on screen, in m), `outline` the meshes outlined while hovered or selected (a grown, front-culled material in `material_overlay`). `get_parts` lists the ones the highlight moves between (all visible parts by default), `get_pickable_parts` the ones the mouse can click.
- `Card`: a `WorldPanel` whose menu is a `StationCard` (`show_part`, `press_primary`). It isn't opened itself: the station passes mouse events to it (`WorldPanel.point`), turns it to face the camera every frame, glides it to the selected part and draws it on top (`set_on_top`), plus an amber leader line (an `ImmediateMesh` ribbon) from its edge to the part.

Input while used: mouse motion hovers the nearest pickable part, a click selects it (`_picked`, e.g. the weapon station lays a rack weapon on the bench); directions (`move_*`, `ui_*`) select the nearest part in that screen direction (`step`, along the direction counts more than across); `tab_prev`/`tab_next` call `_cycle` (the weapon station switches weapons); a station's own keys go to `_shortcut` (the locker's `slot_1`/`slot_2`, keys 1 and 2); `interact`/`ui_accept` call the card's `press_primary`; `pause`/`ui_cancel` close.

- **Upgrade stations:** `UpgradeStation` (`game/stations/upgrade/upgrade_station.gd`) with an `UpgradeCard` (`game/stations/upgrade/upgrade_card.tscn`): `can_buy`/`buy` pay from the nearest ship's hold, locked while a mission is underway. The armor (`armor_station.tscn`, a fitting frame, the player inside) and miners (`miner_station.tscn`, the miner model on a pad, its drill, glass tank and cable outlined) place their parts by hand. `WeaponStation` (`weapon_station.tscn`) builds its rack from `weapons` (an `Arsenal`, every weapon of the game) and lays the picked weapon on the bench; its parts sit at the weapon scene's `MkPips` (damage) and `MagazinePips` (magazine). The weapons shown are their scenes with processing off (`WeaponDisplay`); weapons the player doesn't own are see-through (`GeometryInstance3D.transparency`).
- **Lockers:** `LoadoutStation` (`game/stations/loadout/loadout_locker.tscn`, four in the armory, `number` 1–4) with a `LoadoutCard`. Its parts are every weapon of the game (`weapons`), hanging from `Rack` in rows (`rows_per_column`, then the next column) or lying in `Cradle1`/`Cradle2` when in the loadout; it rearranges whenever the loadout, the owned weapons or the MK levels change. `_cycle` picks `selected_slot` (framed amber on the card, not focused: grabbing the focus every frame cancels a mouse press on the other button), `toggle(weapon, slot)` changes the loadout (`Loadout.assign`) but never takes out the last weapon. Locker `number` belongs to the `number`th node in the players group (`get_owner_player`, `can_use`): the order players join in, until co-op gives them stable seats. The `Door` shows while a mission is underway or nobody owns the locker. `WeaponDisplay` (`game/weapons/weapon_display.gd`) makes the displayed weapons for the rack, bench and lockers, centers them on their holder (weapon models start at their grip) and shows the ones not owned see-through.
- **Navigator and flight console:** `NavigatorStation` (`game/stations/navigator/navigator.tscn`, at the bridge's holo table) has one continuous `zoom` (0: star system, 1: a body, 2: a landing site) that eases towards `zoom_target`; `set_zoom_target` stops short of what can't be reached (`UNREACHABLE_LIMIT`: the star, stations, locked bodies and regions) and shows the region's landing site (`Mission.preview`) when the target reaches 2; choosing it is separate (`choose_destination` → `Mission.choose`, which sets `Mission.destination`; `Mission.confirm` flies to the destination). It keeps its views and zoom when closed (the table goes on showing them) and builds the star system as soon as the mission is there, so the table shows it from the start; it has no `user_spot` (the player uses it from where they stand, its `Use` reaches around the whole table). Its `level` (what the parts are) follows the target. Under `View` it builds `System` (a hologram sphere per planet and moon of `Mission.settings.system`, a ring-and-hub shape per station, moons around the body they orbit, an orbit ring per body, the star in the middle as a part whose item is the `StarSystem`; all its hologram materials fade together) and `Globe` (a sphere with `assets/shaders/region_globe.gdshader`: each surface point belongs to the nearest region center within `region_reach`, borders where regions meet and at their edge; selected and hovered regions are passed in as uniforms). `_show_zoom` scales each view around its anchor (`_zoom_into`: the body, the region's surface point) while moving the anchor to the center, and crossfades into the next view over the last quarter of each step; at the landing site it grows in the `HoloTable`'s location hologram (`set_hologram_scale`, `LANDING_SCALE` so the card beside it leaves it free). Picking on the globe is a ray against the sphere (`_part_at`), the card sits at a fixed spot beside the hologram (`_card_position`), `pause`/`ui_cancel` step back (`_back`), and the wheel arrives through `_shortcut` (new `Station` hooks); `zoom_in`/`zoom_out` (wheel, triggers, +/-) zoom gradually. `FlightStation` (`game/stations/flight/flight_console.tscn`, on the cockpit console) has the launch lever as its part; `launch` calls `Mission.confirm`, and the lever's `Handle` tilts back during the flight. Both cards (`NavigatorCard`, `FlightCard`) refresh every frame from the mission's state. The world is data (`game/world/`: `StarSystem` → `CelestialBody` → `Region`, the greybox system in `game/world/star_system.tres`, referenced by `MissionSettings.system`); `Mission.roll_offers` makes one `MissionBrief` per open region (`StarSystem.open_regions`, `MissionBrief.for_region`: its biome, danger and length) with a new seed after every run, and `Mission.offer_for(region)` finds it.
- **Skill graph:** `SkillStation` (`game/stations/skill_graph/skill_graph.tscn`, in the skills room) with a `SkillCard` (`game/stations/skill_graph/skill_card.tscn`). The skills are data (`game/progression/skills/`): a `Skill` (name, description, `effect`, `ranks` of `SkillRank`s with cost and value, the skill it `requires`, its `graph_position` in the cluster), `SkillCluster`s (name, color, `center` on the graph) in one `SkillTree` (`game/progression/skills/tree/skill_tree.tres`; each skill its own file, since the save refers to them by path), and each player's learned ranks in `Skills` (`Player.skills`; `value(effect)` adds up what the learned skills with that effect do). `Graph` (above the emitter) turns to face the camera every frame and holds a point per skill (a hologram sphere as its `StationPart`, rank pips below ranked ones), links from the required skill, the cluster names and a dark backdrop with a frame. The backdrop draws after the room's see-through things and the hologram after the backdrop (`render_priority`); while used, the backdrop also skips the depth test, since the floor markings below the tilted graph are nearer the camera than it. `can_learn`/`learn` pay the next rank from the hold (locked during a mission, like the upgrades). The view: `Graph/Focus` is the `view_focus`, moved by `set_pan` (kept within `graph_bounds`), and `set_zoom` scales `view_height` (down to `MIN_ZOOM`) around a graph point; `_card_scale` (a new `Station` hook) scales the card with the zoom, so it keeps its size on screen and passes the text size check at any zoom. Mouse: a press away from the card that moves more than `DRAG_THRESHOLD` pans (`_shortcut`, with a ray against the graph's plane), the wheel zooms around the cursor; `zoom_in`/`zoom_out` held zoom around the selected skill; `select` pans to keep the selected skill in view (`_follow`); `_cycle` jumps to the next cluster's root and centers on the cluster. The card goes to `card_spot`: beside the selected skill, trying inwards then outwards, level then half a card down or up, then pushed further sideways, and taking the first spot that covers no other skill and stays in `view_rect` (else the one covering fewest). Closing resets zoom and pan.
- **Bed:** `BedStation` (`game/stations/bed/bed.tscn`, one per player cabin over the cabin's bed prop, `number` 1–4, the beds against the near wall turned around so the use spot is at the foot) with a `BedCard`. `sleep` saves (`SaveGame.save_progress`, not while a mission is underway), hides the card (`Station.show_card`), fades a full-screen black `ColorRect` in (`FADE_TIME`; a transition, not a HUD) with the camera still on the bed, then closes and quits (`quits`, off in tests). Ownership uses `Station.nth_player`, shared with the lockers.
- **Hold:** `OreHold` (`game/stations/hold/ore_hold.gd`, `game/stations/hold/ore_hold.tscn`, in the cargo bay, its origin in the middle of the main lane) builds an `OreTank` (a `StationPart`: a greybox silo built in code, with a collision body and its own `use_point`) per ore of `OreCatalog`, in a cluster per band around a pump hub (sizes in `TANKS`, silos per row in `ROW_LENGTH`; the far row shifted by `window_shift`). The clusters behind the lane line up leftwards from `back_right_edge`, `WALK_WIDTH` apart; the signature cluster ends at `front_right_edge`. `get_clusters` lists them (the tests check the lane, the ways between and to the lift, the ramp button and the windows). It's a station without a `Use` child (`Station.use_point` is optional): a silo's `use_point` selects it and opens the hold. `_cycle` steps through `get_reading_order` (rows from the back, left to right). `get_view_center` follows the selected silo, and `Ship.countdown_hidden` hides the ramp's countdown while it's used. `Ship._set_hold` shows each amount; `Ship.found_ores` (saved with the ship) keeps found ores known when emptied.
- **Wrist display:** `WristDisplay` (`game/player/wrist/wrist_display.gd`, `Player.wrist`) is a `WorldMenu` of its own that opens with the `wrist` action (not through an `Interactable`): a transparent `WorldPanel` with a `WristCard` (`game/player/wrist/wrist_card.tscn`) beside the player and a focus node between the two for the camera. Tabs are labels in `%Tabs`; the cargo is the only one so far.
- **Crew (NPCs):** `Npc` (`game/npcs/npc.gd`, `game/npcs/npc.tscn`) is a station: the person is its one part, its card a `TalkCard`, and `Bubble` a second transparent `WorldPanel` with a `SpeechBubble` (`game/npcs/speech_bubble.tscn`: the line in a panel with a tail drawn below its middle, kept to the bottom of its screen) that faces the camera above the head while they talk (`HEAD_HEIGHT`). Who they are is data: an `NpcProfile` (`game/npcs/npc_profile.gd`; name, translated role, `accent_color` for the collar light, `suit_tint` multiplying the suit's colors, crew `cabin`, `dialogue`), e.g. `game/npcs/crew/quartermaster.tres` with its `Dialogue` and `Topic`s built in. A `Dialogue` has a `greeting` (played by itself while it isn't heard), a `prompt` (the bubble while the list shows) and `topics`; a `Topic` has a stable `id`, a `title`, `lines` (one bubble each), the story flags it `requires` and optionally a `requires_weapon` (only shown to a player who owns it). Texts are the English originals like everywhere (`tools/translations.gd` collects the role, prompt, titles and every line). Hearing a topic to the end sets its `id` in the ship's `Story` (`game/story/story.gd`: a set of flags, saved with the ship; later quest steps and crew joining go there too); `get_choices(listener)` lists the topics open for a player (the one talking by default), `has_news(listener)` drives the amber marker (for the nearest player). While open: `step` moves `choice` up and down the list (the last entry is "Goodbye"), `press` (the card's `press_primary`) plays the highlighted topic or the next line, `leave_topic` (`_back`) returns to the list. `_place_user_spot` puts `user_spot` and the camera's `view_focus` relative to the camera when the talk starts (`USER_DISTANCE` away, turned `USER_ANGLE` towards the screen's left), so the NPC turns three quarters towards the camera and the card on their right stays free. The model is `assets/player/player.glb` with `PlayerAnimator` (`aiming` off: idle); `_turn` yaws `Body` towards the player talking (or the nearest within `NOTICE_RANGE`). Each NPC brings a small spot light, so they read in the dark rooms.
- **Cards fit and read:** `tests/stations/test_menu_fit.gd` shows every upgrade on every station's card, every skill and rank on the skill card, every weapon on the locker card, every crew member's lines in their bubble and every state of their talk card (and opens every terminal) in every language, with the buttons disabled and enabled (the enabled style is wider), and fails when the content needs more than the layout (a card that's too wide spills over both edges of its screen and gets cut off; button rows are `HFlowContainer`s so they wrap instead); it also checks that body text (the theme's 30 px) is at least 2% of the framed view's height (`font size / pixels_per_meter / view_height`). So a card's `pixels_per_meter` follows its station's `view_height` (500 at 2.6–3 m, 400 at 3.6 m).

## 3. CI/CD (GitHub Actions)

| Workflow | Trigger | Steps |
|---|---|---|
| `ci.yml` | PR, merge queue, push to `main` | gdformat check, gdlint, ruff, unit tests (headless Godot), import check |
| `build.yml` | push to `main` | Export Windows + Linux (+ macOS later) builds, upload as workflow artifacts |
| `release.yml` | git tag `v*` | Export builds, create GitHub Release with zipped builds attached |
| `steam-deploy.yml` (later) | release / manual | Upload build to Steam via SteamCMD to a beta branch |

Godot is run headless in CI with matching export templates (version read from `.godot-version`).

`ci.yml` has three jobs, `Lint GDScript` (`tools/lint.sh gdscript`), `Lint Python` (`tools/lint.sh python`) and `Test` (`tools/test.sh`); all are required status checks in the `main` ruleset, so a failing job blocks the merge. The Godot binary and the Git LFS objects are cached between runs (LFS bandwidth quota). The shared setup steps are composite actions in `.github/actions/` (`lfs-pull`, `setup-godot`), so workflows don't repeat them.

`build.yml` runs `tools/export.sh` (also usable locally): it imports the project, then exports a release build of every preset in `export_presets.cfg` to its export path under `builds/` (gitignored); CI uploads them as the `lodestorm-windows` / `lodestorm-linux` workflow artifacts. Presets: Windows Desktop and Linux, x86_64, PCK next to the binary, `tests/` and `addons/gut/` excluded; the godot-ai plugin strips its own autoload from exports. `application/modify_resources` (exe icon and metadata) is off because it needs rcedit, and Wine on Linux CI; turn it on with the release work (M8). `export_presets.cfg` is committed: Godot keeps signing credentials in `.godot/export_credentials.cfg`, never put them in the presets.

Export templates: the full archive is >1 GB, so `setup-godot` (with `export-templates: "true"`) downloads it once per Godot version and caches only the two release templates used. Locally, install them via the editor (Editor → Manage Export Templates), or extract `windows_release_x86_64.exe`, `linux_release.x86_64` and `version.txt` from the archive into Godot's `export_templates/<version>.stable/` folder in its user data directory (Windows `%APPDATA%\Godot`, Linux `~/.local/share/godot`, macOS `~/Library/Application Support/Godot`).

## 4. Asset pipeline

- Blender (via Blender MCP) → export glTF (`.glb`) → `assets/` in Godot.
- `.blend` source files are committed too (open source).
- Binary assets (`.blend`, textures, audio) via **Git LFS** (watch GitHub LFS storage/bandwidth quotas).
- **Swappable models:** a gameplay scene keeps its look under a `Model` child, and its script finds the parts it animates by name among all descendants, so a modeled `.glb` can replace the greybox without code changes. The miner's model provides `Fill` (scaled along Y from 0 to 1 with the fill level, origin at its bottom), `FullLamp`, `HoseOutlet` and meshes named `Frame*`; damage (rust, hit flash, alarm blink) is drawn as an overlay on the `Frame*` meshes, so it works on top of the model's own materials. Blender models are Z-up meters; the glTF export converts to Godot's Y-up.
- **Model kits:** one `.glb` can hold many parts that scenes and resources pick by node name, e.g. all rock variants in `assets/rocks/rocks.glb`. `ModelParts` (`game/models/model_parts.gd`) reads a part's mesh (and transform) from the imported scene without instancing it. A `ScatterType` takes its mesh from `model` + `model_part`; an `OreType` names its `variants` in `model` (each a node with a `Base*` rock mesh and `Crystal*` meshes, drawn in the ore's glowing material), and each `OreNode` shows one of them. Ore badge icons (`assets/ores/icons/<ore>.png`, 256 px) need mipmaps so they stay clean at card size: set `mipmaps/generate=true` in each icon's `.import` (Godot has no per-folder import defaults; `tests/ores/test_ore_glow.gd` checks every ore's icon).
- **Ore kits:** one model kit per ore (`assets/ores/<ore>.glb`, its `.blend` in `assets/ores/source/`), so ores are added and re-baked one at a time. `assets/ores/source/ores_build.py` builds them; each ore is a module `assets/ores/source/ore_types/<ore>.py` with an `ORE = OreSpec(...)` (`ore_geo.py`: its crystal shape function, how the crystals group, preview color, the variants "a", "b" and "wall", optional `dark_body` and `smooth`), so several people (or agents) can work on different ores in parallel without touching the build script. `ores_build.py wip <tag> [ores] [views]` renders previews (the view `types` puts the "a" variants side by side), `final <ore>` saves the procedural `.blend` that `ores_bake.py <ore>` bakes into a 512 atlas, `icon <ores|all>` renders the badge icons (the main crystal group of the "a" variant, without the loose chips). The kits' textures are imported VRAM compressed (the normal map as a normal map, roughness from it), like the other models. A new ore needs its type module, a bake, its icon, its `OreType` resource and an entry in `all_ores.tres`.
- **Model files:** the game imports the `.glb` (e.g. `assets/miners/miner_glow.glb`; Godot extracts its embedded textures next to it). The `.blend` sources live in a `source/` folder with a `.gdignore` next to it, because Godot would import `.blend` files too (through Blender) and duplicate the model. Procedural Blender materials are baked into one texture set per model (base color, ORM, normal) before export. Godot doesn't import glTF transmission, so glass gets a Godot material override in the scene (see `game/mining/miner.tscn`).
- **Characters:** a character `.glb` carries its skeleton and animations. The player (`assets/player/player.glb`) has a skeleton with Godot's humanoid bone names (`SkeletonProfileHumanoid`, no fingers, T-pose rest), so its clips could be retargeted later, and one skinned mesh: hard-surface parts weighted 100 % to their bone, the undersuit limbs blended across elbows and knees. The clips are keyframed by the build script, not by hand: every pose is a set of world-space rotations per bone plus two-bone IK for arms and legs (feet planted on the ground, hands on the blaster's grips), sampled every frame at 30 fps, one Blender action and NLA track per clip. Loops are set in the game (`PlayerAnimator` builds its `AnimationTree` in code), so the `.glb.import` stays default. Markers the game uses are empties on bones (Godot imports them under a `BoneAttachment3D`), and the scene's nodes follow them through a `RemoteTransform3D`, so their paths stay stable. The model faces glTF +Z (Blender -Y), the player's `Body` turns it by 180°. Four-legged aliens (`assets/aliens/swarmer/swarmer.glb`) have their own skeleton: `Body` (moves the whole trunk), `Hips` with the tail and the hind legs, `Spine`, `Chest` with the front legs and the scythes, `Neck`, `Head`, `Jaw`; legs are `<Front|Hind><Left|Right><UpperLeg|LowerLeg|Foot>` (front elbows bend back, hind knees forward, the hind `Foot` is the long metatarsal). Their organic mesh is lofted along the bones and weighted to the two nearest bones; plates, teeth, claws and blades are rigid. The clips (`Idle`, `Run`, `Attack`, `Die`) only move the trunk, head, tail and blades; the legs come from `AlienLegs` (`game/aliens/alien_legs.gd`), a `SkeletonModifier3D` added under the model's `Skeleton3D` at runtime: every foot stays planted until the spot under its hip (plus half a step's travel) is too far away, then steps there in an arc, the diagonal pairs taking turns (a trot); a ray finds the ground under each new step (other characters skipped), and two-bone IK bends the upper and lower leg so the ankle sits above the foot, the foot keeping its animated angle. It works with the interpolated transform, so feet stay put between physics ticks. On death it switches off and `Die` folds the legs. `AlienAnimator` builds the alien's `AnimationTree` in code (idle/run blend by speed, attack one-shot, death).
- **Terrain textures:** the generated ground is drawn with `assets/shaders/terrain.gdshader`, one `ShaderMaterial` per biome (`assets/terrain/<biome>_terrain.tres`, set as the biome's `ground_material`) with three tileable texture sets: ground (6 m tile) and scree (4 m), projected from above, and rock (8 m), projected from the sides with the image's up as the world's up. Hex tiling hides the tiling: every pixel mixes three samples from randomly shifted copies of the texture on a grid of hexagons (ground and scree turned too, rock only shifted sideways so its strata stay level; `hex_cells`, `hex_contrast`), and a large noise varies the brightness (`macro_strength`, `macro_size`). Layers without weight at a pixel aren't sampled, so open ground costs 6 texture reads, cliffs 12. Rock takes over by the slope; scree comes from the vertex color's alpha, which `GeneratedLocation` paints at the foot of steep ground (higher ground within 2 grid points, `LocationTerrain.highest_around`) and in patches; the vertex color's RGB tints the low ground darker and varies the brightness over large areas. Where layers meet, the textures' heights decide (stones and ledges poke through). Each set is two 1024 px PNGs: `<layer>_albedo` (RGB base color, A height) and `<layer>_nra` (RG normal X/Y, B roughness, A AO), imported VRAM compressed in high quality (BPTC) without alpha border fix. They're made by `assets/terrain/source/terrain_textures.py` (`tools/blender.sh assets/terrain/source/terrain_textures.py [layer ...] [preview]`): each layer is real geometry (a displaced ground grid, stones, roots) with procedural materials, surrounded by eight instances of itself so everything tiles, rendered from straight above with an orthographic camera as emission passes (base color, roughness, normal, height, AO); the shader noise is periodic 4D noise on a torus, the numpy maps are filtered noise and wrapped Voronoi cells. `preview` also renders a lit 2×2 tile check to `tmp/terrain/`. Only the script and the PNGs are committed (no `.blend`, the script rebuilds the scenes in about 10 s each; reruns give the same layers, the PNG bytes differ slightly from GPU sampling).
- **Asset scripts:** a modeled asset is built by Python scripts next to its `.blend` (e.g. `assets/miners/source/miner_glow_build.py` models it with procedural materials, `miner_glow_bake.py` bakes the textures and writes the `.blend` and `.glb`), with shared helpers in `tools/blender/`: `common.py` for building (transforms, the `Part` mesh builder, material node helpers, preview scene, renders, contact sheets, export) and `bake.py` for the bake. A bake script only describes its asset in a `bake.Job` (objects sharing the atlas, texture size and supersampling, material name, optional hooks for bake-only props, a custom unwrap or constant materials) and calls `bake.run()`: unwrap into one atlas, bake base color / ORM / normal (and emission), fill the gaps between the islands, swap in one baked PBR material, export, re-import and render checks. It bakes without Blender's bake margin (with several objects, one object's margin paints over the others' islands) and grows the islands itself. `<script> verify` only re-imports and renders the checks; the env var `BAKE_OUT=<dir>` writes the `.glb`, `.blend`, textures and checks to `<dir>` instead, to compare a re-bake without touching `assets/`. Run them headless with `tools/blender.sh <script> [args]`, which needs the env var `BLENDER` (path to the Blender executable). Preview renders and intermediate files go to `tmp/`; only the scripts, the baked `.blend` and the `.glb` are committed.

## 5. Platform services & distribution

### Abstraction

A `PlatformService` layer (autoload) with backends:

- `NullPlatform` — GitHub/itch builds, development, CI (no-op)
- `SteamPlatform` — via [GodotSteam](https://godotsteam.com/) (GDExtension)
- `EpicPlatform` / `GogPlatform` — later, via EOS / GOG Galaxy plugins (to be evaluated)

Gameplay only calls e.g. `PlatformService.unlock_achievement(&"first_miner")`; the game must run fully without any store client.

### Achievements

- Defined once in the game (id, name, description, icon), mirrored in each store's backend config.
- Optional in-game achievement list so non-Steam builds have them too.
- During development Steam's test App ID `480` (Spacewar) is used until the real App ID exists.

### Steam publishing — first-timer checklist

1. Create a Steamworks partner account (identity, tax and bank info).
2. Pay the Steam Direct fee per game (currently USD 100, recoupable after USD 1,000 gross revenue). After payment there is a mandatory waiting period (~30 days) before release.
3. Get the App ID; set up depots (Windows/Linux/macOS), and the SteamPipe upload via SteamCMD.
4. Configure achievements + icons in Steamworks.
5. Build the store page (capsule images, screenshots, trailer, description) → Valve review.
6. "Coming Soon" page must be public for at least ~2 weeks before release (wishlists matter a lot).
7. Upload a build → Valve build review → release (Early Access is an option for an iterating game).

These rules may change; re-verify on the Steamworks documentation when we get there.

### Other stores

Epic Games Store and GOG have their own submission processes and SDKs — evaluated once the game approaches release.
