## 2. Code quality

| Tool | Purpose |
|---|---|
| [godot-gdscript-toolkit](https://github.com/Scony/godot-gdscript-toolkit) `gdlint` | Linting (naming, complexity, ordering); config in `gdlintrc` (only overrides of the defaults) |
| `gdformat` (same toolkit) | Formatting, checked with `gdformat --check`; config in `gdformatrc` |
| Godot GDScript warnings | **Every warning is an error** in the project settings (`debug/gdscript/warnings/*`), so a script with one fails to load and `tests/project/test_scripts_parse.gd` fails in CI: the default warnings (shadowing, integer division, unused variables, ...) and the typing ones Godot ignores by default (`untyped_declaration`, `unsafe_property_access`, `unsafe_method_access`, `unsafe_call_argument`). Where integer division is meant, say so with `@warning_ignore("integer_division")`. `addons/` is exempt (Godot's default `directory_rules`) |
| Unit tests | [GUT](https://github.com/bitwes/Gut) in `addons/gut/` (version in its `plugin.cfg`, must support the pinned Godot version), tests in `tests/` (`test_*.gd`, config `.gutconfig.json`), run headless |
| [ruff](https://docs.astral.sh/ruff/) | Formatting and linting of the Python scripts (Blender asset scripts, `tools/blender/`, the sound synthesis in `assets/audio/source/`); config in `ruff.toml` (ruff's default rules, only overrides; line length 120 because the asset scripts are full of coordinate tables; target: Blender's bundled Python) |
| `.editorconfig` | Consistent whitespace/line endings across editors |

All checks are enforced by CI on every pull request (failing jobs block the merge), not by local git hooks. The same scripts run locally and in CI:

- `tools/lint.sh`: `gdformat --check` + `gdlint` over the project (`addons/`, `local/`, `tmp/` excluded in the rc files), then `ruff format --check` + `ruff check` (ruff skips what git ignores, and `addons/`) and whether the generated ship hull matches its generator (`game/ship/hull_build.py --check`); `tools/lint.sh gdscript` or `tools/lint.sh python` runs only one half. gdtoolkit and ruff are pinned in `requirements-dev.txt`: `pip install -r requirements-dev.txt`, ideally in a `.venv/` (gitignored).
- `tools/test.sh`: imports the project (`tools/import.sh`: fails if the import prints any `ERROR`, e.g. an LFS pointer instead of a file), then runs GUT headless with `$GODOT4_EDITOR`, spread over `TEST_JOBS` parallel processes (default 4; each one's output is printed when all are done). `TEST_SHARD=k/n` runs only the k-th of n shares (CI runs four on parallel runners). The scripts are balanced over the processes of all shares by their durations in `tests/timings.txt`, longest first (a script missing there counts as 10 s); `TEST_REPORTS=<dir>` keeps each process's GUT JUnit report in that directory (CI uploads them as the `test-reports-<share>` artifacts, kept 30 days). `tools/timings.sh` rewrites `tests/timings.txt` from those reports: local directories, CI run IDs, or without an argument the latest three successful CI runs on `main` (needs `gh`); CI's numbers fit CI's runners best. Each script's time is its mean over the runs, since one run's times swing a lot with what shares its runner (the slowest location script took 48–87 s), and scripts that no longer exist are left out. JUnit reports leave out `before_all`, so a script that shares slow work between its tests does it in the first test that needs it. Refresh the timings after adding or splitting slow scripts. Extra arguments go to GUT in a single process instead (e.g. `-gselect=test_foo.gd`). Exits non-zero on failures.
- The slowest tests (sweeps over many generated locations) are split over several scripts so they run in parallel: their planning is in `tests/support/location_sweep.gd`, and the sweep over every region's set pieces (`tests/locations/set_piece_sweep.gd`) takes a share of the locations in each `test_set_pieces_<part>.gd` (`PARTS` of them). A script that takes much longer than the others sets the floor for the whole run: split it.
- Tests run with `--fixed-fps 60` (the physics tick rate): every frame advances exactly one physics tick and simulated time doesn't wait for the wall clock, so `wait_seconds` / `wait_physics_frames` only take as long as computing the frames. Anything that runs in real time (worker threads like location planning, the background bake of the walkable area) must be waited for with `tests/support/real_time.gd` (`await REAL_TIME.wait_until(condition, seconds)`, a wall-clock timeout; assert its result), not GUT's `wait_until`, whose seconds are simulated and run out long before a busy CI runner finishes the work. Wait for the real end state (e.g. the navigation map synced with the baked region, which also can't be queried before its first sync), not for a side effect.
- GUT fails a test on any engine error or warning logged while it runs. Engine warnings that say nothing about the code under test are let through by `tests/support/expected_engine_warnings.gd` (registered in `pre_run.gd`), only by their exact text: so far Jolt's "job system exceeded the maximum number of jobs", which it logs and waits out when every worker thread is busy (four test processes on CI's four cores, physics stepped back to back).
- GUT silently skips test scripts that fail to parse, so `tests/project/test_scripts_parse.gd` loads every project script and fails on parse or typing errors.
- `tools/uids.sh` (`tools/uids.gd`, headless) gives every scene and resource its own UID and every `ext_resource` the UID of its target, as the editor writes them, so references survive moving files; a copied file gets a new UID. Run it after writing or patching `.tscn`/`.tres` files without the editor; `tests/project/test_resource_uids.gd` fails until then.
- Tests that need the map get it from `tests/support/test_map.gd`: the main map with the small hand-built test location instead of the generated outside world (fixed ore nodes, rocks and nests; generating a location takes about a second per test). The ramp button needs a picked mission: `pick_mission(map)` picks the first one on offer (picking reinstances the location).

The game lives in `game/`, one folder per feature: its scenes, scripts and resources together, so a feature is found (and moved, or worked on in parallel) in one place. Imported art stays in `assets/` (the Blender pipeline writes there), tests in `tests/`, mirroring `game/`.

Rules: a folder is named after a game concept, never `utils`/`common`/`core` (a shared helper goes to the feature it serves, or gets its own named folder like `models/`). A scene's tuning `.tres` sits next to it (e.g. `game/player/player_settings.tres`); a feature's content (one resource per ore, weapon, skill, ...) goes in a subfolder (`types/`, `tree/`, `crew/`). Later features (VR, co-op, platform services) get their own folders (`vr/`, `net/`, `platform/`). Developer shell scripts live in `tools/` (ignored by Godot via `.gdignore`).

**The ship** (`game/ship/ship.tscn`) is put together from parts, so the hull and each room can be changed (and later modeled) on their own:

- `hull.tscn`: the greybox hull (floors, walls with doors and windows, the upper deck's slab, roof, nose cone, landing gear, thrusters), generated by `game/ship/hull_build.py` (`python game/ship/hull_build.py`). Don't edit it by hand; the art pass replaces it with the modeled hull.
- `rooms/` (`lower/`, `upper/`, `cargo_bay.tscn`): a scene per room with its floor, light, sign, props, stations and NPCs, edited by hand. `ship.tscn` places each at its floor center under `Rooms/Lower`, `Rooms/Upper` or `Rooms`, so node paths like `Rooms/Lower/Armory/Locker1` stay the same.
- `materials/`: materials used by more than one of these scenes (props, beds, lockers, floor guides).
- `ship.tscn` itself keeps what belongs to the whole ship: the lifts, the floor guides between rooms, the ramp and its button, the boarding and respawn markers, the hold, the countdown and the flight.

The layout (each room's position and size) is defined in `hull_build.py`: moving or resizing a room means changing it there, rebuilding the hull, and moving the room's scene (and resizing its floor) to match.

### Conventions

- Static typing everywhere (`var speed: float = 5.0`, typed function signatures).
- Follow the official GDScript style guide (snake_case files/functions, PascalCase classes/nodes).
- Gameplay logic separated from presentation where it helps testing (e.g. miner fill logic, resource inventory, upgrade math as plain testable classes/resources).
- Tunable values live in `Resource` files (`.tres`), not hardcoded (needed for playtest tuning anyway).

### Cross-platform development

Development must work on Windows (Git Bash), Linux and macOS.

- Scripts are POSIX `sh`/`bash` (no PowerShell/`.bat`-only tooling); avoid GNU-only flags (e.g. `sed -i` differs on macOS) or use Python instead.
- No hardcoded absolute or machine-specific paths; use env vars (`GODOT4_EDITOR`, `BLENDER`, `BLENDER_MCP_PATH`) and paths relative to the repo root.
- Line endings are LF (`.gitattributes`); mark scripts executable in git with `git update-index --chmod=+x` (Windows doesn't keep the bit).
- File names: lowercase, no spaces, never rely on case to distinguish files (Windows/macOS file systems are case-insensitive).
- Platform-specific project settings use Godot feature overrides (e.g. `rendering_device/driver.windows`), never replace the shared default.

### Engine settings

- **Versions:** each version is defined once and referenced everywhere else. Godot: `.godot-version` (read by CI and scripts; when upgrading, also let the editor update `config/features` in `project.godot`). godot-ai: `.mcp.json`, kept equal to `addons/godot_ai/plugin.cfg`.
- Renderer Forward+, Jolt physics, **Vulkan on all platforms** (Godot's default, so `project.godot` has no driver line). D3D12 was rejected: in a sibling project on the same Godot 4.7.2 + SteamVR setup it logged texture errors every frame and the headset image stayed black, while Vulkan worked. Retry D3D12 only after a Godot update and with a reason.
- **Performance targets** (see [`GAME_DESIGN.md`](GAME_DESIGN.md#2-platform--technical-constraints)): desktop 60 FPS minimum, 120–144 target; VR 90 minimum, with two views per frame. Settings follow from that:
  - Display: base resolution 1920×1080 (the reference size for 2D and stretching; 3D renders at the window's native resolution), fullscreen (borderless) by default, also when run from the editor. Window mode and resolution become player settings later.
  - Anti-aliasing: MSAA 2x for 3D (sharp geometry edges, works in VR), no TAA/FXAA (blur and smearing, worst in VR). The level is a starting value, **TBD (playtest)**, later a player setting.
  - Physics interpolation on: physics ticks at 60 Hz while the display runs at 90–144 Hz, interpolation keeps movement smooth without raising the tick rate. Nodes that are moved outside `_physics_process` or teleported need `reset_physics_interpolation()`.
  - Expensive per-`Environment` effects (SDFGI, SSR, volumetric fog) are off by default and only added when a profile shows the budget for them; the art direction leans on rim light and emissive accents for readability instead.
  - Look of the outside (`game/maps/main.tscn`): AgX tonemapping, glow (bloom) only above HDR 1.2, so only emissive parts bloom (ore, eyes, lamps), a dim warm sun, a faint cool back light without shadows and low ambient light. Aboard, `Weather` raises the ambient light (`indoor_ambient_energy`), because the cut-away roof still shades the rooms. Values are **TBD (playtest)**.
  - Rim light: `assets/shaders/rim_light.tres` is a material overlay that adds a cool glow along the outline, independent of the lights (players, aliens, miners). It costs one extra additive pass per mesh that uses it.
  - Ore glow: `OreType.get_material()` (crystals, `assets/shaders/ore_crystal.gdshader`) and `get_glow_material()` (miner column, hose, canisters, `ore_fill.gdshader`) are `ShaderMaterial`s made by `OreGlow` (`game/ores/ore_glow.gd`), shared per ore type, with the ore's `color`, `glow` (the `OreType.Glow` index) and `dark_body` as uniforms; full brightness is emission energy 2.5. Both include `ore_glow_spatial.gdshaderinc` (the crystal shader defines `ORE_CRYSTAL`), and all ore shaders take the rhythms from `ore_glow.gdshaderinc`, which `OreGlow.intensity(glow, time, phase)` repeats in GDScript (change both together; `tests/ores/test_ore_glow.gd` checks the range and that no pattern peaks more than 3 times a second). Flicker is smooth value noise (3.5 steps per second) times a slow noise for dips; wave bands use the mesh's height (object space; for the hose, world height); sparkle hashes each flat-shaded facet's normal to glint at its own time (fill materials only shimmer); breathing brightens the faces towards the camera (a fresnel core); shifting turns the hue around the grey axis, on crystals also by the viewing angle. A dark body is near-black and glossy, with emission only along the edges of 3D cells in object space (`vein_density` per meter, at least about a pixel wide via `fwidth`) and a faint rim; filled things glow dimly between the veins. Each instance gets its own `phase` (an `instance uniform`, `OreGlow.set_phase`, from `OreGlow.phase_at(position)`, set by `OreNode` and `Miner`, so a miner pulses with its deposit); without one the shader takes it from the node's position.
  - Occlusion culling stays off until there are occluders to bake (ship interior, M3); remember to enable it on SubViewports too.
  - Renderer for VR: Forward+ is used for PC VR. Whether Steam Frame standalone needs the Mobile renderer is checked in M6, through a feature override (see above), not by switching the default.
- **Input map** (`[input]` in `project.godot`, checked by `tests/project/test_input_map.gd`): every gameplay action has a keyboard/mouse and a gamepad binding on all devices (developer tools only get a key); keys use physical keycodes so WASD stays in place on non-QWERTY layouts. Mouse aiming uses the cursor position, so `aim_*` only has right-stick bindings. godot-ai can only bind logical keycodes: add keys with the editor closed or via the editor's Input Map tab ("Physical Keycode"). Stick deadzone 0.2 is a starting value, **TBD (playtest)**.

  | `move_left/right/forward/back` | WASD | left stick |
  | `aim_left/right/forward/back` | cursor | right stick |
  | `attack` | left mouse button | RT / R2 |
  | `interact` | E | A / Cross |

- **Navigation:** 0.5 m cells (`navigation/3d/default_cell_size`; navigation meshes must use the same), so baking the generated outside world stays under a second; `merge_rasterizer_cell_scale` is 0.01, which avoids most edge merge errors on its terrain; the few left on some worlds (a handful of unlinked edges among about 12,000 polygons) are harmless, so their warning is off (`navigation/3d/warnings/navmesh_edge_merge_errors`). The map takes a baked mesh over in the background, so paths exist a few frames after the bake. The generated world bakes on its own `WorkerThreadPool` task (`LocationNavigation`), not with `bake_from_source_geometry_data_async`: a region freed mid-bake waits for the task, since quitting while a bake still runs crashes the engine on exit (the async bake can't be waited for, its end is only noticed on the main thread). Aliens search the whole navigation mesh for a path (`path_search_max_polygons = 0` on their agent): around the rock of a generated location, the default limit (4096 polygons) ran out on long ways around, and Godot's fallback search then logged "It's not expect to not find the most reachable polygons" every frame. **Queries are expensive:** Godot 4.7 finds the polygon closest to a point by going through every polygon of every region, so `map_get_closest_point` takes about 0.35 ms and a path look-up (both ends) about 0.5 ms on a generated world (10,000–15,000 polygons), short ways too; baking the world in tiles (one region each) didn't help. So aliens look a path up again only once its end moved 1 m or a fifth of the way, at most two per physics frame (`AlienPathing`), and nothing calls `map_get_closest_point` per frame (burrowers follow the ground with a short ray, backing off holds its spot for half a second).
- **Many aliens** (M4 step 9 A, measured in a late, frenzied tier 6 run with the cap full and the player running): each alien costs about 100–150 µs a frame on screen (leg IK, its `AnimationTree`, skinning and drawing) and its AI, `move_and_slide` and avoidance on top while it moves. A `VisibleOnScreenNotifier3D` (its body's box, grown by 1.5 m for shadows and legs) switches off an alien's `AlienLegs` (`culled`), `AnimationTree` and `_process` (pose, glow) off screen, except the Ravager's (its steps shake the ground); headless nothing is on screen, so `Alien.culls_off_screen` is off there (tests). An alien standing on the ground skips `move_and_slide`, its material is only touched on a change, and fliers push apart only from fliers (`AlienFlight.GROUP`). Setting an alien up costs about 1 ms (the first stalker or tender of a session 12–20 ms), so nests hatch from a queue: one alien per pack every `hatch_gap`, the hive at most one per physics frame; nests at the cap look again every `CAP_RETRY` instead of every tick. Watch out when measuring on Windows: tools polling the GPU driver (e.g. an `nvidia-smi` based exporter) cause 30–50 ms hitches every few seconds, even in an empty scene.
- **Physics layers:** everything collides on layer 1. Layer 2 only stops projectiles (they raycast against every layer; players and aliens only collide with layer 1), e.g. the force field in the ship's shooting range doorway.
- **Location viewer** (`game/debug/location_viewer.tscn`, 2D, developer only): plans generated locations (with the game's isometric view, V toggles it; the white arrow shows where the camera looks) and draws them from above: walkable ground light (darker the lower it lies, with terraces), the barrier brown where it's rock and in the biome's gap tint where it's a gap (white lines for the walls along a gap's edge), bridges lighter, trails' paths darker, buttes as rings, a dry wash's bed as a sandy line, terrace stairs' slabs as squares with their ramps, the hazard in its tint with a ring and its name, the passes, the areas with their kind and walking distance, ore nodes in their ore's colors, nests, the lanes kept free, the map parts in amber (footprint, props, name, a set piece's in capitals, crates as squares, quest sites as diamonds), and in magenta any spot a player could fall to without a way back (should be none). Left/Right change the seed, Up/Down the number of areas, B the biome, G the region (its biome and set pieces), R a random seed, S saves a picture to `user://location_viewer/`. Run it from the editor (F6 on the scene), or for one picture: `"$GODOT4_EDITOR" --path . game/debug/location_viewer.tscn -- --seed=3 --areas=11 --biome=0 --region=0 --view=1 --shot=tmp/layout.png` (`--region`: index into the star system's regions, -1 none).
- **Palette viewer** (`game/debug/palette_viewer.tscn`, 2D, developer only): every color the game uses as tiles in groups (players, ores, the hive, silhouettes, health, ammo, the suit ring, the ship's status, the mission, menus, danger, skill clusters, biomes and bodies on the map, the crew), read from where the game keeps them (the resources, the classes' constants, the weapon scenes' ammo gauges), so new ores, weapons or crew show up by themselves; a color kept somewhere else needs a line in `PaletteViewer.groups()`. Alpha and glow are left out. `ColorVision` simulates the three common color blindnesses (protanopia, deuteranopia, tritanopia at full strength, Machado et al. 2009, in linear RGB) and measures how far apart two colors look (OKLab distance). 0 shows all four visions side by side, 1–4 one of them with the names and the pairs that look closest (under 0.08, **TBD (playtest)**): colors of one group, or of two groups seen together during a run, that look nearly the same with that vision; with a color blindness only the pairs that look apart normally (what it loses), and colors used twice on purpose (under 0.02 normally) are left out. Ores also differ by crystal shape and glow, players by their number, so a close pair there is a hint. The mouse over a tile names it with its hex values, S saves a picture to `user://palette_viewer/`. Check new colors here against the ones they're seen with before using them (run it when colors change; it's not a CI check): from the editor (F6 on the scene), or for one picture `"$GODOT4_EDITOR" --path . game/debug/palette_viewer.tscn -- --vision=2 --shot=tmp/palette.png` (`--vision`: 0 all four, 1 normal, 2–4 the color blindnesses).
- **Debug overlay** (autoload `DebugOverlay`, `game/debug/debug_overlay.gd`): a 2D developer panel, toggled with F3, in English, with two tabs: "State" (the live values and the shortcuts, grouped) and "Tuning" (a folded section of sliders per settings resource). It only exists when the game runs from the editor (`OS.has_feature("editor")`, also true for the headless tests); exported builds, debug ones included, remove it at start. It shows the mission state, the ship's flight phase, time, escalation, player health, how many aliens are left (chasing, hunters, raiders), how many nests there are (and destroyed) and how many miners (broken), has shortcuts (skip to the warning time, storm now, skip the flight, kill / heal players, kill aliens, let every nest hatch a hunter or a raider, take a burst's share of health off every nest (each press one stage), break every miner, unlock every weapon for every player, fill the hold with 900 units of every ore to test the upgrade stations, give ore, add teammates that stand still and remove them, reset the save and reload the map), switches for god mode (players lose no health, hits still flash the suit light and mark the ring; kill players still kills) and the aliens' AI (off: every alien stands where it is without a target or an attack, burrowers come up, they can still be hit and killed; nests keep hatching) and sliders for the settings resources (`TUNING` in the script; add new tuning values there; integer settings get whole-number sliders). Sliders change the loaded resources live, so every scene using them sees the new value; changes last until the game stops and aren't saved, so copy good values into the `.tres` files by hand. A tuned mission duration also moves the running timer. While the mouse is over the panel, the player neither aims nor attacks with it.
- **User data, logs and crashes:** `application/config/use_custom_user_dir` gives the game its own user data folder (`user://`) named after it, instead of Godot's `app_userdata/<name>`: `%APPDATA%\Lodestorm` on Windows, `~/.local/share/Lodestorm` on Linux (or under `$XDG_DATA_HOME`), `~/Library/Application Support/Lodestorm` on macOS; runs from the editor use it too. Godot's file logging (on by default on desktop, release builds too) writes each run to `logs/godot.log` there; the next start renames it to `godot<date>.log`, and the last 5 are kept. There's no crash dump: on a crash Godot's crash handler logs the engine version and a native backtrace (without symbols in release builds: addresses only), and `debug/settings/gdscript/always_track_call_stacks` adds the GDScript call stack to errors and crashes in release builds too (at a small cost per call). A crash inside the GPU driver can end the process before the handler runs; then the log just stops. Players reach the folder with "Open folder" in the settings (`SettingsList.logs_folder`), and the bug report template (`.github/ISSUE_TEMPLATE/bug_report.yml`) asks for the newest log files and names the folder per system.

### Localization

English and German so far (see [`GAME_DESIGN.md`](GAME_DESIGN.md#localization-and-voice)), with gettext PO files in `locale/`: one file per language, plain text, readable in a diff.

- **Texts are the English originals:** a scene's text property (e.g. `Label3D.text`) or `tr("Text")` in a script is the key, and English needs no translation file. Write them in sentence case ("Mess hall"); labels that show capitals set `uppercase`, so translations don't have to shout. `tr("Text", "context")` tells apart texts that read the same but translate differently.
- `locale/lodestorm.pot` is the template with every text. `tools/translations.sh` (`tools/translations.gd`, headless) collects it from `game/` (text properties of nodes, unless their auto translation is disabled; `tr()` calls with string literals; the player-facing texts of resource types listed in `RESOURCE_TEXTS`, e.g. biome names, weapon names and descriptions, also of resources built into another one, like the star system's bodies and regions) and brings every translation listed in the project settings (`internationalization/locale/translations`) up to date: new texts come in untranslated, unused ones go. Run it after adding or changing texts, then fill in the translations.
- `tests/project/test_translations.gd` fails when the template or a translation is out of date, or when a listed translation misses a text, so every new text needs its German translation in the same pull request.
- Nodes translate their texts themselves, also when the language changes while playing. A label whose text is set from code (e.g. the countdowns) disables its auto translation and gets `tr()` results, so nothing is translated twice.
- The game follows the system language (regional variants like `de_AT` use `de`, unknown languages show English); the settings (`SettingsList`, on the pause panel and the settings terminal) switch it while playing and save it (`GameSettings`, see [Saving](#saving)); `--language de` on the command line forces one for testing. The tests always run in English (`tests/support/pre_run.gd`).
- Room for longer texts: German runs about a third longer than English. Floor markings (`FloorGuide`) never get wider than their English text; they wrap between rooms instead and grow away from their arrow, which stays in place.
- **Adding a language:** create `locale/<code>.po` with a header (`Language: <code>`), add it to the translations in the project settings, add the language's own name to `SettingsList.LANGUAGE_NAMES`, run `tools/translations.sh` and translate every entry.

### Saving

What's saved and when: [`GAME_DESIGN.md`](GAME_DESIGN.md#11-death--persistence). A `SaveGame` node in the map (`game/save/save_game.gd`) loads the save when the map starts and writes it.

- **Files:** JSON in `save/` under `SaveGame.directory`: `ship.json` for the host's part (the story's flags (`Ship.story`), the heat shield (`Ship.heat_shield`: its MK level, whether the next plate is the project and what's paid into it), the furnaces unlocked (`Ship.furnaces`) and the body the ship is at (`Mission.at_body`, by its `CelestialBody.id`); later crew and quests) and `player.json` for the local player's (their hold (`Player.hold`, a `PlayerHold`: units per item and the items ever in it), their batches in the furnaces (`Player.refining`: per batch its slot, alloy, bars, bars done and start time in Unix seconds; bars finished since are put into the hold on loading), owned weapons, loadout, upgrade levels, skill ranks, crafted miners (`Player.fleet`: per miner its number, whether it goes along, its parts' levels and levels under way, its build while it's built; where the lost ones were left)), split for co-op (see [Co-op progression](GAME_DESIGN.md#co-op-progression)). The settings are in `settings.cfg` (`ConfigFile`, `game/save/game_settings.gd`: the language, and the suit ring's size and "Always show" in static vars read every frame, `ring_scale`) next to `save/`, so resetting keeps them.
- **Where:** the game's user data folder (`user://`, see [Engine settings](#engine-settings)); runs from the editor use `user://dev/`, so the debug overlay's shortcuts never reach a real save. The tests never touch either: `tests/support/pre_run.gd` sets `SaveGame.directory` to empty (nothing is loaded or saved), and `tests/save/test_save_game.gd` uses its own folder.
- **When:** on every change of the hold, the story, the arsenal, the loadout, the upgrades, the skills or the miners (`changed`, batched to one write per frame) unless a mission is underway (`Mission.is_underway`), and when a mission is returned or lost.
- **Format:** each file has a `version` (`SaveGame.VERSION`); raise it and convert older saves in `SaveGame._read` when the format changes. Newer saves aren't read. Ore types, weapon types, upgrades and skills are saved by their UID (`uid://...`), so they can be moved and renamed; version 1 saved `res://` paths, which `SaveGame.MOVED` maps to where the files are now; up to version 2 the hold was in `ship.json`, and loading moves it into the player's (`SaveGame._ship_hold`); up to version 3 the miner upgrades were the player's, and loading moves their levels (and a level under way) onto M-01 (`SaveGame._move_miner_levels`). Entries that don't resolve to the expected resource type are skipped with a warning; weapons are never taken away and the locker never empties the loadout, so a save without a known (owned) weapon keeps the default arsenal (loadout) instead of leaving the player unarmed. A save that was older or needed repairs is written again right after loading; a file that can't be parsed is kept as `<file>.corrupt` and the game starts from the defaults. Files are written to `<file>.tmp` first and then renamed, so a crash never leaves half a save.
- **Reset:** `SaveGame.reset_progress` deletes `save/` and reloads the map, only while `SaveGame.is_solo` (no connected peers and at most one player; hosting a session alone counts, since friends can join any time); the settings terminal disables its button otherwise.
- **Language:** the saved one is applied when the map enters the tree, unless the command line forced another one (`--language`; detected as a locale other than the system's, so forcing the system language doesn't win).

### 3D menus

Menus are things in the world (see [`GAME_DESIGN.md`](GAME_DESIGN.md#ui-in-the-world-not-on-the-screen)), each a `WorldMenu` (`game/ui/world_menu.gd`): one player uses it at a time (`open`/`close`, `Player.menu`), and while they do, the camera frames it (`view_height`, `view_focus`). There are two kinds: screens (`WorldPanel`, on terminals) and stations (`Station`, the object is the menu).

**Screens:** a `WorldPanel` (`game/ui/world_panel.tscn`) renders a normal Control scene (`menu`) in a SubViewport onto an unshaded quad. A `Terminal` (`game/ui/terminal.tscn`, an `Interactable`) is a console with such a screen; set its `menu` to the Control scene. The settings terminal in cabin 1 shows `game/ui/settings_menu.tscn` (the only terminal left: system things only).

- **Items:** `ItemType` (`game/items/item_type.gd`) is the base of everything a hold keeps (`OreType`, `AlloyType`): its name, color, glow pattern (`ItemType.Glow`), dark body and badge icon (`get_badge_icon`: an alloy without an icon draws an ingot with its tier's ticks, `IngotIcon`), so holds, cards and tests handle every kind the same way. `PlayerHold` keeps a player's units per item (`ores()` gives the ores for the cards, whose costs are ore costs until alloys join them).
- **Item badges:** `ItemBadge` (`game/items/item_badge.gd`) shows an item on a card: its `ItemType.icon` (a white crystal silhouette with grey facets on transparent) through `assets/shaders/ore_badge.gdshader`, which tints the greys in the ore's color and plays its glow pattern (from `ore_glow.gdshaderinc`; sparkle per grey level, i.e. per facet; shifting turns the hue; a dark body is a dark icon with a colored rim and facet edges), and optionally its translated name. An item without an icon gets a four-facet crystal drawn in code (`ItemBadge.fallback_icon`). The navigator, flight and cost (`ItemCost`, `game/ui/item_cost.gd`) rows list ores as badges with their names in `HFlowContainer`s, so they wrap; the cards are sized for six ores with the longest names (`tests/stations/test_menu_fit.gd`).
- **Building a menu:** a Control scene filling its viewport, laid out for `size * pixels_per_meter` (960 × 600 for the default 1.2 × 0.75 m screen), with `assets/ui/terminal_theme.tres` (fonts 30 px, titles 46 px with the `Title` variation; a focus style that stands out, since gamepads navigate by focus). Texts go through translations like any scene (see Localization). A control closes its menu with `WorldPanel.showing(self).close()`.
- **Using:** `open(player)` sets `Player.menu`; the player then ignores movement, aiming and actions (an action still held when the menu opens or closes waits for its release, so the closing press doesn't act in the world). The `IsoCameraRig` moves to the menu (or its `view_focus`, e.g. a station's object and its card) and zooms until it sees `view_height` m (1.6 for a terminal, a station sets its own, **TBD (playtest)**; a `Terminal` passes both on to its panel). The screen material switches to no depth test while used and renders after the player's silhouette and rim light (`ON_TOP_PRIORITY`), so a player standing in front doesn't hide it.
- **Input:** while open, the panel takes the events in `_input`. Mouse events become a ray from the camera; `pixel_at(origin, direction)` turns it into a menu pixel, and the event is pushed into the SubViewport (`push_input(event, true)`: layout coordinates). A VR controller will use `pixel_at` the same way. Other events are translated into GUI actions (`NAVIGATION`: `move_*` and `ui_*` directions, `interact` and `ui_accept`), so the menus use Godot's focus navigation; a held stick presses once, held keys repeat. `pause` and `ui_cancel` close.
- **Sharpness:** the SubViewport keeps its layout size as `size_2d_override` (stretched) and renders at about the pixels the screen covers on the display, in half-octave steps (`_update_resolution`): zoomed in on a 4K display that's 2× the layout, from the isometric distance 1/8 (viewport textures have no mipmaps, so a big texture would shimmer). Fonts re-rasterize at that size (viewport oversampling), so text stays crisp.
- **Testing:** push input into the root viewport with `push_input(event, true)`: without it the window rescales the position (a headless window is tiny). Headless, the window is too small to test the render resolution; check it with a windowed probe.

**Stations** (`game/stations/station.gd`, each station in its own folder, e.g. `game/stations/navigator/`): an object whose parts are the menu. The scene's root is the `Station` (or a subclass); children:

- `Use`: an `Interactable` (with an optional `Highlight`) that opens it; disabled while used. It sits at the object's center: `interact_range` counts from its `footprint` (a rectangle on the floor, e.g. a bench or a bed) or, without one, from its center (round objects: their radius plus the reach), so players use it from any side.
- `view_focus` and `view_height` frame the object and the card. The player using it stays where they stood when they used it and looks at the selected part (`get_look_target`).
- `StationPart`s (`game/stations/station_part.gd`): the selectable parts. `item` is what the part stands for (an `Upgrade` at an upgrade station), `pick_radius` how close the mouse cursor must be (screen distance to its center), `card_offset` where the card floats (right/up on screen, in m), `outline` the meshes outlined while hovered or selected (a grown, front-culled material in `material_overlay`). `get_parts` lists the ones the highlight moves between (all visible parts by default), `get_pickable_parts` the ones the mouse can click.
- `Card`: a `WorldPanel` whose menu is a `StationCard` (`show_part`, `press_primary`). It isn't opened itself: the station passes mouse events to it (`WorldPanel.point`), turns it to face the camera every frame, glides it to the selected part and draws it on top (`set_on_top`), plus an amber leader line (an `ImmediateMesh` ribbon) from its edge to the part.

Input while used: mouse motion hovers the nearest pickable part, a click selects it (`_picked`, e.g. the weapon station lays a rack weapon on the bench); directions (`move_*`, `ui_*`) select the next part in that screen direction (`step` asks `_neighbor`: by default `_nearest_on_screen` of `room_parts`: the nearest part within `CONE` (60°) of the direction on screen, else the most nearly straight on (along the direction counting more than across); the locker and the weapon station move along their racks' grid instead, since a rack seen in perspective while the camera glides tilts its lines on screen). For stations sharing a `room` (`&"cargo_bay"`: `OreHold`, the furnaces, the `IngotRack`), `room_parts` are the parts of every usable station of the room not used by someone else, and stepping onto another one's part hands the user over (`hand_over`: close, select, open; `Station.of(part)` finds a part's station); `tab_prev`/`tab_next` call `_cycle` (the locker and the weapon station jump a row, the silos and the rack step through their own parts, a furnace through its recipes); a station's own keys go to `_shortcut` (the locker's `slot_1`/`slot_2`, keys 1 and 2); `interact`/`ui_accept` call the card's `press_primary`; `pause`/`ui_cancel` close.

- **Upgrade stations:** `UpgradeStation` (`game/stations/upgrade/upgrade_station.gd`) with an `UpgradeCard` (`game/stations/upgrade/upgrade_card.tscn`): `can_buy`/`buy` pay from the hold of the player using it (`Player.hold`), locked while a mission is underway. `get_levels` is the `Upgrades` it buys into (the user's; the miners' bay: the miner on its pad). The armor (`armor_station.tscn`, a fitting frame, the player inside) places its part by hand. The miners' bay (`MinerBayStation`, `game/stations/miner_bay/miner_bay.tscn`) has the pad's parts by hand (the miner itself at its floor plate, drill, glass tank, cable and side boxes outlined) and builds its six `MinerCradle`s in code along `Cradles` (each a `StationPart` with a stowed miner at a third of its size and its plate; one being built or empty drawn with `miner_ghost.gdshader`, a see-through outline denser below `fill_top`); its `MinerCard` (an `UpgradeCard` with the parts' pip rows) shows the pad's miner, an empty cradle (build cost as items, `ItemCost.show_items`) or one being built, and a cradle's card floats towards the camera below the row (`_card_position`). Its card is bigger in the world for its wider view (`view_height` 6.6, the same text size on screen). `WeaponStation` (`weapon_station.tscn`, right of the weapons room's door) hangs `weapons` (an `Arsenal`, every weapon of the game) on its `Rack`, a `WeaponRack` (three columns, growing up), and lays the picked weapon on the bench. Its rack weapons aren't in `get_parts` but `_neighbor` reaches them (up from the bench's top part, down from the rack's bottom line back); selected, the `UpgradeCard` shows them with "Lay on the bench" (`show_pick`, `picking`), placed beside the rack (`_beside_rack`) with the camera between weapon and card. `_cycle` lays the first weapon of the next row on the bench; else `get_view_center` shifts halfway along the rack towards the bench weapon's place; its parts sit at the weapon scene's `MkPips` (damage) and `MagazinePips` (magazine). The weapons shown are their scenes with processing off (`WeaponDisplay`); weapons the player doesn't own are see-through (`GeometryInstance3D.transparency`).
- **Weapon racks:** `WeaponRack` (`game/stations/weapon_rack.gd`) hangs an `Arsenal` in rows by `WeaponType.origin` (enum order, top to bottom; within a row the arsenal's order; an origin without weapons gets no row), centered on its origin with the rows going down (`spacing`, `row_spacing`, `label_space` above each row for its name; `columns` wraps a long row onto more lines; `grow_up` puts the bottom line at its origin instead of the top one), a `Label3D` naming each row (`origin_name`, re-set on `NOTIFICATION_TRANSLATION_CHANGED`), and resizes its `panel` (and `collision`) to cover them (`panel_to_floor` for a wall standing on the floor); `show_for(player)` shows MK levels and owned weapons, `get_order` is the hanging order, `get_top` the panel's top edge, `get_half_width` half its width; `neighbor(part, direction)` and `row_start(part, step)` move a highlight over it as a grid (skipping hidden weapons). `WeaponWall` (`game/stations/loadout/weapon_wall.tscn`, in the middle of the armory) is one that shows its `viewer` (the player using a locker whose `wall` it is, else the first local player) and their loadout's slot numbers under the weapons (`get_tag`).
- **Lockers:** `LoadoutStation` (`game/stations/loadout/loadout_locker.tscn`, four in the armory, `number` 1–4, each with the armory's `wall`) with a `LoadoutCard`. Its parts are a part per cradle (`Cradle1`/`Cradle2`, `get_cradle_part`, a display of the weapon in that slot, hidden while empty, selected first on opening) and the wall's weapons (`get_part`); a selected weapon in a cradle stays selected when it moves (the other cradle, or the wall). It relays the cradles whenever the loadout or the MK levels change. While a wall weapon is selected (`is_on_wall`), `_card_position` puts the card above the wall over it (`CARD_GAP`), and the camera frames the weapon and the card (`get_view_center`, `wall_view_height`, also checked by the readable text rule). `_neighbor` moves along the wall's grid and between it and the cradles, `_cycle` jumps a row. Selecting a cradle selects its slot, and an empty slot becomes `selected_slot` whenever the loadout changes (framed amber on the card, not focused: grabbing the focus every frame cancels a mouse press on the other button), `toggle(weapon, slot)` changes the loadout (`Loadout.assign`) but never takes out the last weapon. Locker `number` belongs to the `number`th node in the players group (`get_owner_player`, `can_use`): the order players join in, until co-op gives them stable seats. The `Door` shows while a mission is underway or nobody owns the locker. `WeaponDisplay` (`game/weapons/weapon_display.gd`) makes the displayed weapons for the racks, bench and cradles, centers them on their holder (weapon models start at their grip) and shows the ones not owned see-through.
- **Navigator and flight console:** `NavigatorStation` (`game/stations/navigator/navigator.tscn`, at the bridge's holo table) has one continuous `zoom` (0: star system, 1: a body, 2: a landing site) that eases towards `zoom_target`; `set_zoom_target` stops short of what can't be reached (`UNREACHABLE_LIMIT`: the star, stations, locked bodies and regions) and shows the region's landing site (`Mission.preview`) when the target reaches 2; choosing it is separate (`choose_destination` → `Mission.choose`, which sets `Mission.destination`; `Mission.confirm` flies to the destination). It keeps its views and zoom when closed (the table goes on showing them) and builds the star system as soon as the mission is there, so the table shows it from the start; its `Use` reaches around the whole table. Its `level` (what the parts are) follows the target. Under `View` it builds `System` (a hologram sphere per planet and moon of `Mission.settings.system`, a ring-and-hub shape per station, moons around the body they orbit, an orbit ring per body, the star in the middle as a part whose item is the `StarSystem`; all its hologram materials fade together) and `Globe` (a sphere with `assets/shaders/region_globe.gdshader`: each surface point belongs to the nearest region center within `region_reach`, borders where regions meet and at their edge; selected and hovered regions are passed in as uniforms). `_show_zoom` scales each view around its anchor (`_zoom_into`: the body, the region's surface point) while moving the anchor to the center, and crossfades into the next view over the last quarter of each step; at the landing site it grows in the `HoloTable`'s location hologram (`set_hologram_scale`, `LANDING_SCALE` so the card beside it leaves it free). Picking on the globe is a ray against the sphere (`_part_at`), the card sits at a fixed spot beside the hologram (`_card_position`), `pause`/`ui_cancel` step back (`_back`), and the wheel arrives through `_shortcut` (new `Station` hooks); `zoom_in`/`zoom_out` (wheel, triggers, +/-) zoom gradually. `FlightStation` (`game/stations/flight/flight_console.tscn`, on the cockpit console) has the launch lever as its part; `launch` calls `Mission.confirm`, and the lever's `Handle` tilts back during the flight. Both cards (`NavigatorCard`, `FlightCard`) refresh every frame from the mission's state. The world is data (`game/world/`: `StarSystem` → `CelestialBody` → `Region`, the greybox system in `game/world/star_system.tres`, referenced by `MissionSettings.system`); `Mission.roll_offers` makes one `MissionBrief` per open region (`StarSystem.open_regions`, `MissionBrief.for_region`: its biome, danger and length) with a new seed after every run, and `Mission.offer_for(region)` finds it.
- **Skill graph:** `SkillStation` (`game/stations/skill_graph/skill_graph.tscn`, in the skills room) with a `SkillCard` (`game/stations/skill_graph/skill_card.tscn`). The skills are data (`game/progression/skills/`): a `Skill` (name, description, `effect`, `ranks` of `SkillRank`s with cost and value, the skill it `requires`, its `graph_position` in the cluster), `SkillCluster`s (name, color, `center` on the graph) in one `SkillTree` (`game/progression/skills/tree/skill_tree.tres`; each skill its own file, since the save refers to them by path), and each player's learned ranks in `Skills` (`Player.skills`; `value(effect)` adds up what the learned skills with that effect do). `Graph` (above the emitter) turns to face the camera every frame and holds a point per skill (a hologram sphere as its `StationPart`, rank pips below ranked ones), links from the required skill, the cluster names and a dark backdrop with a frame. The backdrop draws after the room's see-through things and the hologram after the backdrop (`render_priority`); while used, the backdrop also skips the depth test, since the floor markings below the tilted graph are nearer the camera than it. `can_learn`/`learn` pay the next rank from the hold (locked during a mission, like the upgrades). The view: `Graph/Focus` is the `view_focus`, moved by `set_pan` (kept within `graph_bounds`), and `set_zoom` scales `view_height` (down to `MIN_ZOOM`) around a graph point; `_card_scale` (a new `Station` hook) scales the card with the zoom, so it keeps its size on screen and passes the text size check at any zoom. Mouse: a press away from the card that moves more than `DRAG_THRESHOLD` pans (`_shortcut`, with a ray against the graph's plane), the wheel zooms around the cursor; `zoom_in`/`zoom_out` held zoom around the selected skill; `select` pans to keep the selected skill in view (`_follow`); `_cycle` jumps to the next cluster's root and centers on the cluster. The card goes to `card_spot`: beside the selected skill, trying inwards then outwards, level then half a card down or up, then pushed further sideways, and taking the first spot that covers no other skill and stays in `view_rect` (else the one covering fewest). Closing resets zoom and pan.
- **Bed:** `BedStation` (`game/stations/bed/bed.tscn`, one per player cabin over the cabin's bed prop, `number` 1–4, the beds against the near wall turned around so the use spot is at the foot) with a `BedCard`. `sleep` saves (`SaveGame.save_progress`, not while a mission is underway), hides the card (`Station.show_card`), fades a full-screen black `ColorRect` in (`FADE_TIME`; a transition, not a HUD) with the camera still on the bed, then closes and quits (`quits`, off in tests); the saving, fading and quitting are `ScreenFade.quit_game` (`game/ui/screen_fade.gd`), shared with the pause panel. Ownership uses `Station.nth_player`, shared with the lockers.
- **Heat shield:** `HeatShieldStation` (`game/stations/heat_shield/drive_core.tscn`, in the engine room) with a `HeatShieldCard`. The shield is data and state: `ShieldPlate`s (their cost) in `game/progression/heat_shield/plates.tres` (`ShieldPlates`), and the ship's `HeatShield` (`Ship.heat_shield`: `mk`, `project`, `paid`; `reaches(body)`, `missing`, `take_from` pays and installs, `level_changed` when the MK level changes). `Ship.store_haul` (called by `Mission` with the whole haul of a returned run) lets the project take its part first; `Ship.pay_shield` pays from the hold. Reach replaces a flag per region: `CelestialBody.is_reachable(shield_mk)`, `StarSystem.open_regions(shield_mk)` and `is_open`; `Mission` offers the newly open regions on `level_changed`, and the navigator rebuilds its hologram. The station builds its plates in code (a closed ring mesh per plate, so the selection outline is a border; the fill is an arc over the camera's side, `FRONT_ARC`), each plate's `StationPart.item` its `ShieldPlate`; `is_host` is `multiplayer.is_server()` until co-op. `ShipFlight.fly(to_body)` takes the longer departure (`FlightSettings.travel_time`) when `Mission.confirm` crosses to another body (`Mission.ship_body`), with a sphere in the body's color growing behind the hull.
- **Hold:** `OreHold` (`game/stations/hold/ore_hold.gd`, `game/stations/hold/ore_hold.tscn`, in the cargo bay, its origin in the middle of the main lane) builds an `OreTank` (a `StationPart`: a greybox silo built in code, with a collision body and its own `use_point`) per ore of `OreCatalog`, in a cluster per band around a pump hub (sizes in `TANKS`, silos per row in `ROW_LENGTH`; the far row shifted by `window_shift`). The clusters behind the lane line up leftwards from `back_right_edge`, `WALK_WIDTH` apart; the signature cluster ends at `front_right_edge`. `get_clusters` lists them (the tests check the lane, the ways between and to the lift, the ramp button and the windows). It's a station without a `Use` child (`Station.use_point` is optional): a silo's `use_point` selects it and opens the hold. `_cycle` steps through `get_reading_order` (rows from the back, left to right). `get_view_center` follows the selected silo, and `Ship.countdown_hidden` hides the ramp's countdown while it's used. It shows a `PlayerHold` (`show_hold`): the user's while it's used, else the viewer's (`Ship.viewer`, or the first local player), following its `item_changed`; `PlayerHold.found` (saved with the player) keeps found ores known when emptied. `Ship.store_haul` puts each run's haul, after the heat shield's share, into every player's hold.
- **Refinery:** `Refinery` (`game/stations/refinery/refinery.tscn`, in the cargo bay's front corner, its `hold` the `OreHold`) holds four `FurnaceStation`s (`furnace.tscn`, `slot` 0–3) and an `IngotRack` (`ingot_rack.tscn`) in a row, builds the manifold over the flues and a pipe from each of the hold's `Hub`s (deferred, once the silos are built), and every `TICK` puts the bars every player's batches finished by then into their hold (`Refining.update(hold, now)`; `now` is always passed in, so tests run the clock). A furnace is a greybox built in code with its door as its one part; `_cycle` steps the recipe (`step_recipe`), the card's `BAR_BUTTONS` and `zoom_out`/`zoom_in` (`_shortcut`) call `step_bars` (`bars`, read through `get_bars`: 1 up to `get_max_bars`, what the hold pays for), the directions are the `Station`'s, `start`/`stop` pay and refund through `Refining` (`stop` only arms on the first press, for `STOP_CONFIRM_TIME`), and it shows `get_shown_player`'s batch (the user's, else `Ship.get_viewing_player`, which the silos use too). `FurnaceCard` and `RackCard` show it; `RackShelf` stacks up to `SHOWN_BARS` bars in a `MultiMeshInstance3D` (`bar_position`) with a steady emissive material per alloy (`bar_material`; the silos' fill shader is too bright for a full shelf). The rack plays the clink on its shelf from the shown player's `Refining.bars_finished`; the furnace starts and stops its roar loop with the shown batch.
- **Pause panel:** `PausePanel` (`game/player/pause/pause_panel.tscn`, inheriting `world_panel.tscn`; `Player.pause_panel`, loaded in `_ready` since its scripts refer back to the player's) is a transparent `WorldPanel` that opens itself with `pause` when its `holder` has no menu (`can_open`), not through an `Interactable`. It runs while the game is paused (`PROCESS_MODE_ALWAYS`), keeps beside the player facing the camera (`_place`, with a `Focus` node between the two for the camera) and shows a `PauseCard` (`game/player/pause/pause_card.tscn`) with pages (`Page`: main, settings, credits, the quit question; `back` steps back, see below). Solo (`SaveGame.is_solo`) it sets `SceneTree.paused` while open (`pausing`) and lets go when someone joins or it leaves the tree; `NOTIFICATION_APPLICATION_FOCUS_OUT` opens it while `pause_on_focus_loss` (a static, off in the tests and for probes). `IsoCameraRig` runs while paused too (not shaking), so it frames the panel. `quit` asks first during a run (`loses_run`), then `ScreenFade.quit_game` (`quits`, off in tests). Tests that wait while paused set their own node to `PROCESS_MODE_ALWAYS` (GUT's awaiter is its child) and the map to `PROCESS_MODE_PAUSABLE`.
- **Pages:** a `WorldPanel`'s `pause`/`ui_cancel` call its menu's `back() -> bool` first when it has one and only close when that returns false (the pause card, the settings terminal's credits).
- **Settings and credits:** `SettingsList` (`game/ui/settings_list.tscn`: the language buttons, the suit ring's size buttons and its "Always show" switch, the volumes, "Open folder" for the log files (`logs_folder`); `languages`, `current_language`, `LANGUAGE_NAMES`) is the one settings component, in the pause card and in the terminal's `SettingsMenu` (which adds "Reset progress" and a credits page, `show_credits`). `Credits` (`game/ui/credits.tscn`, a `ScrollContainer`) names the team and the tools (`TEAM`, `TOOLS`) and adds Godot's license (`Engine.get_license_text`), its components' copyrights (`Engine.get_copyright_info`) and their license texts (`Engine.get_license_info`) at `SMALL_FONT_SIZE`; `ui_up`/`ui_down` scroll it by `scroll_step`, `scroll_speed` scrolls it by itself.
- **Title view:** `TitleView` (`game/ui/title/title_view.tscn`, in `game/maps/main.tscn` at the hull's middle) is a `WorldMenu` the first player uses from the start (deferred), so they stand still; it turns to the camera's basis on opening (its children are laid out on the screen's plane: `Name` and `Prompt` `Label3D`s, `Credits` a `WorldPanel` drawn on top with a `title_credits.tscn`), snaps the camera there (`IsoCameraRig.snap`), and sets `Ship.show_outside` (the closed hull) and `Ship.countdown_hidden`. `Focus` drifts slowly (`drift`, `drift_period`). `is_button` (a key, mouse or joypad button press, not an echo) closes it; after `credits_delay` without input the credits scroll (`credits_speed`). `TitleView.shows` (static) is off in the tests (`tests/support/pre_run.gd`) and for probes that want the map right away.
- **Crew (NPCs):** `Npc` (`game/npcs/npc.gd`, `game/npcs/npc.tscn`) is a station: the person is its one part, its card a `TalkCard`, and `Bubble` a second transparent `WorldPanel` with a `SpeechBubble` (`game/npcs/speech_bubble.tscn`: the line in a panel with a tail drawn below its middle, kept to the bottom of its screen) that faces the camera above the head while they talk (`HEAD_HEIGHT`). Who they are is data: an `NpcProfile` (`game/npcs/npc_profile.gd`; name, translated role, `accent_color` for the collar light, `suit_tint` multiplying the suit's colors, crew `cabin`, `dialogue`), e.g. `game/npcs/crew/quartermaster.tres` with its `Dialogue` and `Topic`s built in. A `Dialogue` has a `greeting` (played by itself while it isn't heard), a `prompt` (the bubble while the list shows) and `topics`; a `Topic` has a stable `id`, a `title`, `lines` (one bubble each), the story flags it `requires` and optionally a `requires_weapon` (only shown to a player who owns it). Texts are the English originals like everywhere (`tools/translations.gd` collects the role, prompt, titles and every line). Hearing a topic to the end sets its `id` in the ship's `Story` (`game/story/story.gd`: a set of flags, saved with the ship; later quest steps and crew joining go there too); `get_choices(listener)` lists the topics open for a player (the one talking by default), `has_news(listener)` drives the amber marker (for the nearest player). While open: `step` moves `choice` up and down the list (the last entry is "Goodbye"), `press` (the card's `press_primary`) plays the highlighted topic or the next line, `leave_topic` (`_back`) returns to the list. `_place_focus` puts the camera's `view_focus` between them and the player (where the player stands) when the talk starts, a little to the right on screen (`FOCUS_RIGHT`), so the card on their right stays in view. The model is `assets/player/player.glb` with `PlayerAnimator` (`aiming` off: idle); `_turn` yaws `Body` towards the player talking (or the nearest within `NOTICE_RANGE`). Each NPC brings a small spot light, so they read in the dark rooms.
- **Cards fit and read:** `tests/stations/test_menu_fit.gd` shows every upgrade on every station's card, every skill and rank on the skill card, every weapon on the locker card, every crew member's lines in their bubble and every state of their talk card (and opens every terminal) in every language, with the buttons disabled and enabled (the enabled style is wider), and fails when the content needs more than the layout (a card that's too wide spills over both edges of its screen and gets cut off; button rows are `HFlowContainer`s so they wrap instead); it also checks that body text (the theme's 30 px) is at least 2% of the framed view's height (`font size / pixels_per_meter / view_height`). So a card's `pixels_per_meter` follows its station's `view_height` (500 at 2.6–3 m, 400 at 3.6 m).

## 3. CI/CD (GitHub Actions)

| Workflow | Trigger | Steps |
|---|---|---|
| `ci.yml` | PR, merge queue, push to `main` | gdformat check, gdlint, ruff, unit tests (headless Godot), import check |
| `build.yml` | push to `main` | Export Windows + Linux (+ macOS later) builds, upload as workflow artifacts |
| `release.yml` | git tag `v*` | Export builds, create GitHub Release with zipped builds attached |
| `steam-deploy.yml` (later) | release / manual | Upload build to Steam via SteamCMD to a beta branch |

Godot is run headless in CI with matching export templates (version read from `.godot-version`).

`ci.yml` has the jobs `Lint GDScript` (`tools/lint.sh gdscript`), `Lint Python` (`tools/lint.sh python`) and `Test 1/4` to `Test 4/4` (a matrix, `tools/test.sh` with `TEST_SHARD`, each importing the project on its own runner), gathered by `Test`, which passes only when every share passed. `Lint GDScript`, `Lint Python` and `Test` are required status checks in the `main` ruleset, so a failing job blocks the merge; when changing the number of shares, change the matrix and `TEST_SHARD` together. The Godot binary and the Git LFS objects are cached between runs (LFS bandwidth quota). The shared setup steps are composite actions in `.github/actions/` (`lfs-pull`, `setup-godot`), so workflows don't repeat them.

`build.yml` runs `tools/export.sh` (also usable locally): it imports the project, then exports a release build of every preset in `export_presets.cfg` to its export path under `builds/` (gitignored); CI uploads them as the `lodestorm-windows` / `lodestorm-linux` workflow artifacts. Presets: Windows Desktop and Linux, x86_64, PCK next to the binary, `tests/` and `addons/gut/` excluded; the godot-ai plugin strips its own autoload from exports. `application/modify_resources` (exe icon and metadata) is off because it needs rcedit, and Wine on Linux CI; turn it on with the release work (M8). `export_presets.cfg` is committed: Godot keeps signing credentials in `.godot/export_credentials.cfg`, never put them in the presets.

Export templates: the full archive is >1 GB, so `setup-godot` (with `export-templates: "true"`) downloads it once per Godot version and caches only the two release templates used. Locally, install them via the editor (Editor → Manage Export Templates), or extract `windows_release_x86_64.exe`, `linux_release.x86_64` and `version.txt` from the archive into Godot's `export_templates/<version>.stable/` folder in its user data directory (Windows `%APPDATA%\Godot`, Linux `~/.local/share/godot`, macOS `~/Library/Application Support/Godot`).

## 4. Asset pipeline

- Blender (via Blender MCP) → export glTF (`.glb`) → `assets/` in Godot.
- `.blend` source files are committed too (open source).
- Binary assets (`.blend`, textures, audio) via **Git LFS** (watch GitHub LFS storage/bandwidth quotas).
- **Swappable models:** a gameplay scene keeps its look under a `Model` child, and its script finds the parts it animates by name among all descendants, so a modeled `.glb` can replace the greybox without code changes. The miner's model provides `Fill` (scaled along Y from 0 to 1 with the fill level, origin at its bottom), `FullLamp`, `HoseOutlet` and meshes named `Frame*`; damage (rust, hit flash, alarm blink) is drawn as an overlay on the `Frame*` meshes, so it works on top of the model's own materials. Blender models are Z-up meters; the glTF export converts to Godot's Y-up.
- **Model kits:** one `.glb` can hold many parts that scenes and resources pick by node name, e.g. all rock variants in `assets/rocks/rocks.glb`. `ModelParts` (`game/models/model_parts.gd`) reads a part's mesh (and transform) from the imported scene without instancing it. A `ScatterType` takes its mesh from `model` + `model_part`; an `OreType` names its `variants` in `model` (each a node with a `Base*` rock mesh and `Crystal*` meshes, drawn in the ore's glowing material), and each `OreNode` shows one of them. Ore badge icons (`assets/ores/icons/<ore>.png`, 256 px) need mipmaps so they stay clean at card size: set `mipmaps/generate=true` in each icon's `.import` (Godot has no per-folder import defaults; `tests/ores/test_ore_glow.gd` checks every ore's icon).
- **Ore kits:** one model kit per ore (`assets/ores/<ore>.glb`, its `.blend` in `assets/ores/source/`), so ores are added and re-baked one at a time. `assets/ores/source/ores_build.py` builds them; each ore is a module `assets/ores/source/ore_types/<ore>.py` with an `ORE = OreSpec(...)` (`ore_geo.py`: its crystal shape function, how the crystals group, preview color, the variants "a", "b" and "wall", optional `dark_body` and `smooth`), so several people (or agents) can work on different ores in parallel without touching the build script. `ores_build.py wip <tag> [ores] [views]` renders previews (the view `types` puts the "a" variants side by side), `final <ore>` saves the procedural `.blend` that `ores_bake.py <ore>` bakes into a 512 atlas, `icon <ores|all>` renders the badge icons (the main crystal group of the "a" variant, without the loose chips). The kits' textures are imported VRAM compressed (the normal map as a normal map, roughness from it), like the other models. A new ore needs its type module, a bake, its icon, its `OreType` resource and an entry in `all_ores.tres`.
- **Model files:** the game imports the `.glb` (e.g. `assets/miners/miner_glow.glb`; Godot extracts its embedded textures next to it). The `.blend` sources live in a `source/` folder with a `.gdignore` next to it, because Godot would import `.blend` files too (through Blender) and duplicate the model. Procedural Blender materials are baked into one texture set per model (base color, ORM, normal) before export. Godot doesn't import glTF transmission, so glass gets a Godot material override in the scene (see `game/mining/miner.tscn`).
- **Characters:** a character `.glb` carries its skeleton and animations. The player (`assets/player/player.glb`) has a skeleton with Godot's humanoid bone names (`SkeletonProfileHumanoid`, no fingers, T-pose rest), so its clips could be retargeted later, and one skinned mesh, generated (see Generated models below) in an A-pose and fitted by the build script: the skeleton's joints and bone lengths are the suit's (a joint table measured on the mesh), every vertex belongs to the bone nearest to it (the distance to the bone's segment minus the bone's radius; above the hips, what's behind the back only to the torso), blended with the neighbor bone within a band across each joint, faces joining parts that move apart (forearm and hips, arm and flank) are cut, and the mesh is moved into the T rest pose by the inverse of the skinning (the feet only turned, so the soles stay on the ground). The collar's glowing ring becomes `SuitLight`: a thin band following the collar (radius and height per direction around the neck), weighted like the suit under it, with the ring painted over in the texture; the other glowing cyan of the base color (lamps, the backpack's panel) becomes the emission map. The bake keeps the generated UV layout. `CargoRack` and `HosePort` are placed on the backpack measured on the mesh. The clips are keyframed by the build script, not by hand: every pose is a set of world-space rotations per bone plus two-bone IK for arms and legs (feet planted on the ground, hands on Harl's grips), sampled every frame at 30 fps, one Blender action and NLA track per clip. Melee poses place a weapon by its grip: `hold()` turns the right hand so the `WeaponGrip` marker lands on a spot with the weapon pointing a given way (`fist()` for Clout's gauntlet: the fist along the punch), `left_on()` puts the left fist on a point of the weapon given in its scene's axes; a shield (`WeaponType.Hold.SHIELD`) hangs on the `ShieldGrip` marker on the left forearm instead (the player's `ShieldMount`); `player_build.py clips` renders workbench contact sheets of the melee clips with rough stand-in weapons on the grip. Loops are set in the game (`PlayerAnimator` builds its `AnimationTree` in code), so the `.glb.import` stays default. Markers the game uses are empties on bones (Godot imports them under a `BoneAttachment3D`), and the scene's nodes follow them through a `RemoteTransform3D`, so their paths stay stable. The model faces glTF +Z (Blender -Y), the player's `Body` turns it by 180°. Aliens (`assets/aliens/<strain>/<strain>.glb`) are built by one script per strain (`assets/aliens/<strain>/source/<strain>_build.py` and `_bake.py`) on the shared creature kit `tools/blender/creature.py` (the skeleton from a bone table, the organic mesh builder weighting to the two nearest bones, body profiles and plates hugging them, the hive's materials Sinew, Chitin, Bone and Mouth, posing and clip baking), so every strain reads as one species; strains with extra channels (the spitter's sac scales) bake their own clips. The swarmer is generated instead (see Generated models): its build script takes the skeleton's joints from a table measured on the mesh, in the mesh's own standing pose (the rest pose, so nothing is moved), weights every vertex to its nearest bone like the player's suit, cuts the lower jaw from the skull (except at the hinge), and puts the `Eyes` where the texture's eyes glowed; its blades hang from the `Neck`. They have their own skeleton: `Body` (moves the whole trunk), `Hips` with the tail and the hind legs, `Spine`, `Chest` with the front legs and the scythes, `Neck`, `Head`, `Jaw`; legs are `<Front|Mid|Hind><Left|Right><UpperLeg|LowerLeg|Foot>` (the swarmer, warden, gnawer, brute and shrieker have four: front elbows bend back, hind knees forward, the hind `Foot` is the long metatarsal; mite, spitter, burrower, bloater and tender have six, the middle ones under `Spine`, every knee bent out at rest), plus strain bones (the mandibles, a `Sac` with scale keys on the spitter, the shrieker (under `Neck3`, its neck has three bones) and the bloater, the tender's `Tendril<n>A/B/C/Tip`). Meshes: `Creature` (the baked body), `Eyes` and `Glands` (constant emissive, both flare during a wind-up). Their organic mesh is lofted along the bones and weighted to the two nearest bones; plates, teeth, claws and blades are rigid. The clips (`Idle`, `Run`, `Attack`, `Die`) only move the trunk, head, tail and blades; the legs come from `AlienLegs` (`game/aliens/alien_legs.gd`), a `SkeletonModifier3D` added under the model's `Skeleton3D` at runtime: every foot stays planted until the spot under its hip (plus half a step's travel) is too far away, then steps there in an arc, in two sets taking turns (four legs: the diagonal pairs, a trot; six: tripods, front and hind of one side with the middle of the other; the strain's `stride` scales the steps); a ray finds the ground under each new step (other characters skipped), and two-bone IK bends the upper and lower leg so the ankle sits above the foot, the foot keeping its animated angle. It works with the interpolated transform, so feet stay put between physics ticks. On death it switches off and `Die` folds the legs. `AlienAnimator` builds the alien's `AnimationTree` in code (idle/run blend by speed, attack one-shot, death). `AlienPose` moves the model's parent (`Body`) on top of the clips until the art pass brings clips for them: the crouch of a wind-up, the arc of a leap (the legs switch off in the air and plant again on landing), rearing up when staggered, a jolt per hit.
- **Aliens' data:** a strain is an `AlienStrain` (`game/aliens/alien_strain.gd`: its body `scene`, health, armor and its arc, stagger threshold and time, knockback, movement, ranges, `cap_share`, and `attacks`, tried in order); `AlienStrain.spawn(role)` hatches one, so nests only refer to strains. Besides its body and movement a strain has its `tier`, its `role` (a nest hatches guards, hunters and raiders from the strains of that role; `weight` picks among the guards' and raiders' strains), `leash` (guards stay within it of their `Alien.home`, where they hatched, and walk back), `keep_away` (backing off, the spitter) and burrowing (`burrows`: under the ground the alien's collision is off, it moves along the ground (a short ray finds it) without physics and stops under rocks and cliffs, `is_hittable()` is false for shots, swings and the target lock, and a `BurrowRipple` shows it). An attack is an `AlienAttack` resource (`game/aliens/attacks/`: damage, reach, cooldown, `wind_up`, `recovery`, whether it's used on miners) whose kind decides when it can start and what it does (`AlienBite`, `AlienPounce`, `AlienSpit` lobbing an `AcidGlob` that leaves an `AcidPuddle`, `AlienEruption` from under the ground, `AlienSlam` hitting every player around a spot ahead; `clip_lead` starts the model's attack clip that long before the hit, for a clip that is the telegraph and moves the legs itself (the warden's rear-up: `AlienLegs` is off until the attack ends); `underground` says from where an attack starts, `approach()` how close the alien comes for it); each strain's attacks are their own files beside it, so the debug overlay can tune them. More kinds: `AlienCharge` (the brute: a `ChargeLine` of decals on the ground during the wind-up, the alien's `attack_facing` held on it, then a running `lunge` that ignores players' collision and hits everyone in the lane; a stall, `lunge_stalled`, dazes it through `stagger_for`), `AlienScream` (boosts every alien around through `AlienStatus.boost`, emits `Alien.called_for_help`, a `ScreamWave` ring) and `AlienBurst` (kills its alien; its `on_death` leaves an `AcidCloud`, an `AcidPuddle` that hurts aliens too). Attacks get hooks: `prepare` (the wind-up starts), `finish` (the attack ends or is broken off) and `on_death`. `AlienStrain.armored_stagger` is the share of stagger hits on the armor fill, `AlienStrain.mend` an `AlienMend` (`game/aliens/support/`) for which the alien adds `MendLinks`: strands (a `CylinderMesh` per link with `mend_link.gdshader`, from the tendrils' tip bones) to the most hurt aliens near it, healing them and raising their `AlienStatus.bonus_armor`. `AlienStatus` (`Alien.status`) holds what acts on an alien from outside: the scream's boost, the frenzy's `hive_speed` and a tender's link (kept off `Alien`, which is at gdlint's 20 public methods); while `is_buffed()` the alien scales its `Model` up (`BUFFED_SCALE`) and swaps its rim light for a yellow-green one. `Alien` runs the phases (wind-up, act, recovery), the stagger meter and the push, and offers attacks `strike`, `lunge`/`lunge_step`, `stagger_for` and `reach_to`. Weapons hand aliens a `Hit` (`game/weapons/hit.gd`: damage, stagger, push, direction, point, attacker); `Alien.take_hit` applies armor and returns the damage that got through (for the damage readout), `take_damage` is plain damage (burning ground, debug). `HitSpray` (`game/aliens/hit_spray.gd`) is a one-shot `CPUParticles3D` that frees itself. The hive (`game/aliens/hive/hive.tres`, an `AlienHive`) lists every strain and the packs (`AlienPack`: how many of each strain, a weight); `AlienHive.table(tier, biome, preview, seed)` builds a `HatchTable` (from which escalation each strain hatches, the biome's `favored_strains`), which `GeneratedLocation` hands to all its nests (hand-placed nests build their own from the mission's tier). A nest picks packs for hunters and single guards and raiders from it (`HatchTable.pick_single`); hunters and raiders out count by cap share. Every second a nest sums up the working miners whose nearest nest it is (`raider_draw_factor`), which speeds up its raider countdown; `AlienNest.is_frenzied` (from the mission's warning on) sets `status.hive_speed` on its aliens each frame and uses the end values for hunters; it connects every alien it hatches to `called_for_help` and lets the nest nearest to the scream `answer_call` (a pack now, boosted by the scream's values the signal carries, a mouth flare and a `ScreamWave`, then `call_cooldown`). The signal is emitted by `AlienScream` and answered by nests, since nothing a strain loads may reach `AlienNest` (see below). Fliers (`AlienStrain.flight_height` > 0, the darter): `Alien.flight` (`AlienFlight`) turns the horizontal velocity into one that holds the height over the ground (rays on the `WORLD` layer below it and a bit ahead, never below its target's ground), skips the navigation mesh and avoidance and pushes fliers apart; the scene's collision mask is 0, so it bumps into nothing; `AlienDive` (an `AlienCharge` with its line laid on the ground) sets `flight.low` while it acts and recovers; a dead flier drops to the ground. `AlienStrain.cloak` (an `AlienCloak`) adds `Alien.cloaking` (`AlienCloaking`): it swaps the `Creature` mesh's material for `cloak.gdshader` (the screen texture bent along the normals, which writes the stencil like the other bodies, so the occluded silhouette still only shows behind cliffs) while it isn't fully shown, fades `Eyes` and `Glands` through `GeometryInstance3D.transparency`, and turns off its shadow and rim light; `PlayerAim.is_lockable` skips it while `is_hidden()`. `AlienStrain.retreat_time` makes it back off after every attack (`_end_attack`). An attack started while cloaked sets `AlienCloaking.ambush`, which raises the next `Alien.strike` to `AlienCloak.ambush_damage`. `AlienHook` (only once the stalker is fully shown) launches a `FleshHook`: a straight hook with a sinew line (a stretched `CylinderMesh`), a ray per step on `SHOTS` (aliens and players other than prey skipped), that catches a player with `GroundContact.snare` (a timed share of the walking speed, counted down by the player's `tick`; no pull). `AlienStrain.circles` makes an alien between `keep_away` and its reach move around its target (`Alien._chase`), and `AlienAttack.on_the_move` keeps it moving through an attack's wind-up and recovery: the skimmer's `AlienSpit` with `arc_per_meter` 0 is a straight bolt. The apex (`AlienHive.apex`, the Ravager) isn't in `strains`: `GeneratedLocation._add_apex` rolls `AlienHive.apex_chance_at(tier)` with its own RNG from the seed (the rest of the generation stays the same) and adds an `ApexLair` with the route (the middles of reachable areas at least `APEX_LANDING_DISTANCE` from the landing site); the lair spawns it with the mission's tier factors in `_ready`, like nests hatch guards. With `AlienStrain.roams` an alien without a target walks to a random point of `Alien.route` after another; `AlienStrain.tremor` adds `Alien.tremor` (`AlienTremor`), which `AlienLegs.stepped` (a foot landing) and `AlienSlam` thump: `DustPuff`s at the foot and `IsoCameraRig.tremble` on every rig whose target is within `REACH`. `AlienShed` spawns its strain beside the alien as hunters, under the cap read from `alien_nest_settings.tres`. Players' and aliens' meshes are on `RenderLayers.CHARACTERS` (`game/world/render_layers.gd`), and so is what players carry and what floats around them (the weapon, the cargo tubes, the armor pips, the ship pointer, arriving ore, the pause panel; put there where it's built). A `ChargeLine`'s and the `AimReticle`'s decals only reach `RenderLayers.WORLD`, so lanes don't paint them red and the reticle stays on the ground. The suit ring, the miners' rings and the target brackets are on `RenderLayers.MARKINGS`: they're drawn pulled towards the camera (`ground_marking.gdshaderinc`), so a decal reaching them would paint a shifted copy of itself on them; an `Interactable`'s `Highlight` goes there too. The reticle's `normal_fade` (`AimReticle.NORMAL_FADE`) fades it out on steep surfaces instead of smearing it down their sides. Ground markings to read are on `RenderLayers.MARKINGS` too: the stations' stand rings, the rooms' names, the floor guides, a lobbed weapon's landing ring, a throw's sight line, a placed charge's ring. What's light, not a surface, is on `RenderLayers.EFFECTS`: holograms (the holo table's location, the navigator's view, the skill graph, the ghost miners, the outlines of heat shield plates not built yet, holo cards and their leader lines), fields (the shooting range's barrier, Mantle's), weapons' and aliens' effects, the flight's clouds and streaks, and text and plates. Whatever builds such a thing puts it there (`RenderLayers.put` or `layers`); `tests/world/test_render_layers.gd` walks the map and fails on text, sprites, particles, shader or see-through materials left on `WORLD` (except the ship's windows). Hive colors live on `Alien` (`COLOR_GLOW`), not on the nest: a script a strain's scene depends on must not reach `AlienNest`, since through `Mission` and `GeneratedLocation` (which preloads the nest scene, which refers to the strain) that loops back to the strain while it loads. **Destroyable nests:** a nest's `Body` is a `Destructible` (`game/weapons/destructible.gd`, a `StaticBody3D` in its own group: health, armor, `take_hit`/`take_damage`, `damaged` and `destroyed`), so weapons and the target lock reach nests without referring to `AlienNest` (the player's weapons are in an alien's dependency graph, see above): `Projectile` and `SwingDelivery` hit it besides aliens, `PlayerAim.target` and `Weapon.aim_target` are an `Alien` or a `Destructible` (`PlayerAim.is_lockable`, `PlayerAim.aim_point`; aliens are tried first) and `DamageNumber.show_hit` takes either. `AlienNest` sets the body's values (`max_health()`: tier and players), sets `AlienStatus.defending` on its guards on a hit (`Alien._update_target` takes that player first while within the leash), counts the bursts due from the body's health, warns, `_burst`s and shows the model's `Cracks<stage>` meshes; on `destroyed` it leaves `AlienNest.GROUP` (so draw, screams, surges and the overlay skip the husk), emits its own `destroyed` (for the quests' "clear nests" goal), lets every other nest `surge()` and collapses (model scale, own copies of the mound's and slime's materials, a lower collision cylinder).
- **Terrain textures:** the generated ground is drawn with `assets/shaders/terrain.gdshader`, one `ShaderMaterial` per biome (`assets/terrain/<biome>_terrain.tres`, set as the biome's `ground_material`) with three tileable texture sets: ground (6 m tile) and scree (4 m), projected from above, and rock (8 m), projected from the sides with the image's up as the world's up. Hex tiling hides the tiling: every pixel mixes three samples from randomly shifted copies of the texture on a grid of hexagons (ground and scree turned too, rock only shifted sideways so its strata stay level; `hex_cells`, `hex_contrast`), and a large noise varies the brightness (`macro_strength`, `macro_size`). Layers without weight at a pixel aren't sampled, so open ground costs 6 texture reads, cliffs 12. Rock takes over by the slope; scree comes from the vertex color's alpha, which `GeneratedLocation` paints at the foot of steep ground (higher ground within 2 grid points, `LocationTerrain.highest_around`) and in patches; the vertex color's RGB tints the low ground darker and varies the brightness over large areas. Where layers meet, the textures' heights decide (stones and ledges poke through). Each set is two 1024 px PNGs: `<layer>_albedo` (RGB base color, A height) and `<layer>_nra` (RG normal X/Y, B roughness, A AO), imported VRAM compressed in high quality (BPTC) without alpha border fix. They're made by `assets/terrain/source/terrain_textures.py` (`tools/blender.sh assets/terrain/source/terrain_textures.py [layer ...] [preview]`): each layer is real geometry (a displaced ground grid, stones, roots) with procedural materials, surrounded by eight instances of itself so everything tiles, rendered from straight above with an orthographic camera as emission passes (base color, roughness, normal, height, AO); the shader noise is periodic 4D noise on a torus, the numpy maps are filtered noise and wrapped Voronoi cells. `preview` also renders a lit 2×2 tile check to `tmp/terrain/`. Only the script and the PNGs are committed (no `.blend`, the script rebuilds the scenes in about 10 s each; reruns give the same layers, the PNG bytes differ slightly from GPU sampling).
- **Sound effects** (see [Sound](GAME_DESIGN.md#sound)): synthesized by `assets/audio/source/build.py` (Python's standard library only, run with the system Python): `synth.py` is the kit (oscillators with anti-aliasing, noise, envelopes, biquad filters with sweeps, struck partials, echo, a small reverb, the finishing: DC removal, trimming the silent tail, short fades, the peak at -1 dBFS) and registers the recipes; a recipe is a function `(rng, take, variant) -> samples` in a module per group (`weapons.py`, `player.py`, `aliens.py`, `mining.py`, `mission.py` with the biomes' hazards, `refinery.py`, `stations.py`), decorated with `@sound("<group>/<name>", variants=)` (`loop=True` for a loop: the recipe makes `loop_seconds(s)`, the build crossfades its end into its start and writes a WAV sampler chunk looping it whole, which Godot's importer reads as the loop points; the listening page loops it) (a new sound can have `takes="abc"` to compare, the recipe branching on `take`; once one is picked, the others are removed). Every variant is seeded from its name, take and number, so a rebuild writes the same bytes. `python assets/audio/source/build.py [name ...]` writes the take the game uses as `assets/audio/sfx/<group>/<name>_<n>.wav` (16-bit mono, 44.1 kHz; Godot's importer compresses them with QOA, its default) and lists every sound with how it was made (`made_by`), its variants and the recordings it uses in `assets/audio/source/manifest.json`; `--takes <dir>` writes every take with `listen.html` (pick a take per sound, add notes, copy the summary) for picking by ear, e.g. into `tmp/sfx/takes/`. Recorded raw files go in `assets/audio/source/recordings/` with an entry in the manifest's `recordings` (source URL, author, license `CC0-1.0` or `CC-BY-4.0`) and are named in the recipe's `recordings`; the build refuses a recording that isn't listed with an allowed license, and `tests/project/test_sound_licenses.gd` checks every built file against the manifest. The source folder has a `.gdignore`. **Replacing a placeholder:** save the new sound over `assets/audio/sfx/<group>/<name>_<n>.wav` (16-bit WAV, mono for sounds in the world, any rate; keep the names; with more or fewer variants, also add or remove them in the `.tres`'s randomizer and change `variants`), set its manifest entry's `made_by` to how it was made instead of `"build.py"` (e.g. the AI model and its version, `"recorded"`, the tool; this is also the list for Steam's AI content disclosure) and list the recordings it uses (each with its `recordings` entry and raw file). The build then never overwrites it, and its recipe can be deleted. An AI model's license must allow selling the game (see `planned/sfx.md`). In the game, each sound is a `Sound` resource next to its files (`assets/audio/sfx/<group>/<name>.tres`: an `AudioStreamRandomizer` with the variants and the random pitch, the bus, `volume_db`, `limit`, `unit_size`, `max_distance`), referenced by the scenes and settings that play it (e.g. `WeaponType.attack_sound`); a new variant count means adding its streams there. The autoload `Sfx` (`game/audio/sfx.gd`) plays them: `play_at(sound, where, critical)` as an `AudioStreamPlayer3D` under itself (pausable), `play_ui(sound, bus)` flat (always, e.g. a volume slider's sample), `play_loop_at(sound, holder)` / `play_loop(sound, holder)` a loop under the node that makes it (following it, pausing with it, outside the limits) until `stop_loop` or the node goes; `play_at` takes a pitch (an alien strain's `voice_pitch`), which stretches its length; it counts each sound's voices down by its `length()` (the dummy audio driver of headless runs never finishes a stream), drops the farthest beyond the limit, ducks the Effects and Ambience buses while a critical cue plays and applies `GameSettings.volume` to the buses (`game/audio/bus_layout.tres`) every frame. Its `played(sound, critical)` signal is for tests. The listener is an `AudioListener3D` in `PlayerSounds`, made current for the local player; `PlayerSounds` also plays a step per `STEP_LENGTH` walked: a ground hazard's own `step_sound` while the player stands in it (shards, mud), else the deck's when a ray down hits something under a `Ship`, else the ground's. The other sounds come from where they happen: `AlienSounds` (each alien's child: chitter, strikes, hits, death; the attacks' `wind_up_sound` and `act_sound`), the nest, the miner (its loops), the ship (the ramp), the vent, and `MissionSounds` (the weather's child: the warning, the countdown, the storm, for the local viewer). **SceneTree scripts** (`-s`) compile before the autoloads exist, so a probe that refers to game classes (which refer to `Sfx`) fails to compile: load the probe's game code at runtime from a small loader script, or start the work after the first frame (`tools/translations.gd` awaits `process_frame` in `_initialize`).
- **Generated models (image to 3D):** `tools/trellis.py <image> <out.glb> [--seed --faces --texture]` runs TRELLIS.2 on a local ComfyUI (0.34 or newer, its native nodes; the models it needs are listed in the script): background removal (BiRefNet), shape and texture, remeshed, decimated to `--faces` and baked into one textured `.glb` (base color, metallic/roughness, normal, AO), about 4 minutes on a 16 GB GPU, which it uses fully (run one at a time). The input is a concept image made for it: one character, front view, a relaxed A-pose with the arms clear of the body, empty open hands, no weapon or anything strapped on (fused parts can't be rigged apart; weapons are their own models). The raw output and its input are sources: `assets/<asset>/source/trellis/` holds the concept image, the generated `.glb` and `trellis.json` (what made them: models with their licenses, prompt, seeds, settings, date); the build script fits and rigs it (see Characters) with the shared helpers in `tools/blender/generated.py` (loading and welding the raw mesh, the nearest-bone weights with blends across the joints, cutting the faces between parts that move apart, reading and repainting its texture). Generated so far: the player's suit and the swarmer. Licenses: TRELLIS.2 and BiRefNet are MIT, Z-Image Turbo (the concept images) Apache-2.0; DINOv3 (TRELLIS.2's image encoder) has its own license, which doesn't address outputs (we don't ship its weights, so its "Built with DINOv3" notice doesn't apply). Every generated asset counts as pre-generated AI content for Steam's disclosure (see the checklist below).
- **Asset scripts:** a modeled asset is built by Python scripts next to its `.blend` (e.g. `assets/miners/source/miner_glow_build.py` models it with procedural materials, `miner_glow_bake.py` bakes the textures and writes the `.blend` and `.glb`), with shared helpers in `tools/blender/`: `common.py` for building (transforms, the `Part` mesh builder, material node helpers, preview scene, renders, contact sheets, export) and `bake.py` for the bake. A bake script only describes its asset in a `bake.Job` (objects sharing the atlas, texture size and supersampling, material name, optional hooks for bake-only props, a custom unwrap or constant materials) and calls `bake.run()`: unwrap into one atlas, bake base color / ORM / normal (and emission), fill the gaps between the islands, swap in one baked PBR material, export, re-import and render checks. It bakes without Blender's bake margin (with several objects, one object's margin paints over the others' islands) and grows the islands itself. `<script> verify` only re-imports and renders the checks; the env var `BAKE_OUT=<dir>` writes the `.glb`, `.blend`, textures and checks to `<dir>` instead, to compare a re-bake without touching `assets/`. Run them headless with `tools/blender.sh <script> [args]`, which needs the env var `BLENDER` (path to the Blender executable). Preview renders and intermediate files go to `tmp/`; only the scripts, the baked `.blend` and the `.glb` are committed.

## 5. Platform services & distribution

### Abstraction

A `PlatformService` layer (autoload) with backends:

- `NullPlatform`: GitHub/itch builds, development, CI (no-op)
- `SteamPlatform`: via [GodotSteam](https://godotsteam.com/) (GDExtension)
- `EpicPlatform` / `GogPlatform`: later, via EOS / GOG Galaxy plugins (to be evaluated)

Gameplay only calls e.g. `PlatformService.unlock_achievement(&"first_miner")`; the game must run fully without any store client.

### Achievements

- Defined once in the game (id, name, description, icon), mirrored in each store's backend config.
- Optional in-game achievement list so non-Steam builds have them too.
- During development Steam's test App ID `480` (Spacewar) is used until the real App ID exists.

### Steam publishing: first-timer checklist

1. Create a Steamworks partner account (identity, tax and bank info).
2. Pay the Steam Direct fee per game (currently USD 100, recoupable after USD 1,000 gross revenue). After payment there is a mandatory waiting period (~30 days) before release.
3. Get the App ID; set up depots (Windows/Linux/macOS), and the SteamPipe upload via SteamCMD.
4. Configure achievements + icons in Steamworks.
5. Build the store page (capsule images, screenshots, trailer, description) → Valve review.
6. "Coming Soon" page must be public for at least ~2 weeks before release (wishlists matter a lot).
7. Upload a build → Valve build review → release (Early Access is an option for an iterating game).
8. Fill in the AI content disclosure (pre-generated content): the generated models (each `source/trellis/trellis.json`) and sounds (`made_by` in `assets/audio/source/manifest.json`).

These rules may change; re-verify on the Steamworks documentation when we get there.

### Other stores

Epic Games Store and GOG have their own submission processes and SDKs, to be evaluated once the game approaches release.
