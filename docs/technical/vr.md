# VR

How the VR view is built (the design: [`design/vr.md`](../design/vr.md)). Code in `game/vr/`.

## Starting in VR

- **A launch option:** OpenXR is off in the project (`xr/openxr/enabled` stays false) and VR starts with Godot's `--xr-mode on`: starting OpenXR on every launch would start SteamVR on desktop too, and log errors without a headset. From the source: `tools/vr.sh` (the active OpenXR runtime, e.g. SteamVR, starts with it). In a build, the same argument (a Steam launch option "Play in VR" later, M8).
- **Project settings:** `xr/shaders/enabled` (the shaders' multiview variants, needed for stereo), `xr/openxr/default_action_map` (`game/vr/openxr_action_map.tres`). Vulkan, as everywhere (D3D12 showed a black headset in a sibling project, see [`engine.md`](engine.md)); MSAA without OpenXR depth submission (with both, SteamVR logged an error every frame in the same project).
- **The `Vr` autoload** (`game/vr/vr.gd`) checks whether OpenXR runs (`XRServer.find_interface("OpenXR")` initialized); if so it turns the main viewport to the headset (`use_xr`), turns off vsync (the headset paces the frames) and physics object picking (not supported in stereo; the game doesn't use it), and adds the `VrRig` and the `VrGamepad` as its children, so they last across scene changes (the boot screen hands over to the main scene). It centers the view when the session begins and on the runtime's recenter (`pose_recentered`), and quits when the runtime ends the session. Without OpenXR (desktop, the tests) it does nothing.

## The viewpoint

- **`VrRig`** (an `XROrigin3D` with the head, an `XRCamera3D`): the tracking space is centered on the head (`XRServer.center_on_hmd(RESET_BUT_KEEP_TILT, false)`, also zeroing the height), so the origin is where the eyes are. Each frame (after the desktop rig, `process_priority`; also while paused) it reads where the desktop rig is going (`IsoCameraRig.goal`, `goal_zoom`, `framing`: a `CameraZone` or `WorldMenu`), puts the goal on the rig camera's line `VrSettings.distance × goal_zoom` back from it (`VrRig.head_goal`, level: yaw only), and glides there (`follow_speed`). A change of `framing`, a goal farther than `blink_distance` or the rig's `snapped` blinks (black over `blink_time`, jump, clear again). Without a desktop rig (the boot screen) the head sits at the scene's first `Camera3D`. A new scene's own current camera is taken back each frame. The black is an unshaded sphere around the head drawn over everything (`no_depth_test`); it also shows the `ScreenFade`s (2D layers don't reach the headset; the rig takes the darkest in their group).
- **The desktop rig runs on:** `IsoCameraRig` decides where the view goes in both modes, and its camera keeps moving, just not drawn. `ViewCamera.of(node)` returns it in VR (else the viewport's camera): everything laid out for the view (billboards, cards, the suit ring's screen up, walking and aiming relative to the view, station parts picked by direction) uses it, so turning the head never turns the layout. Use `ViewCamera.of` for such code, not `get_viewport().get_camera_3d()`; the sound (`Sfx`, `PlayerSounds`) keeps the viewport's camera, so the ears turn with the head.
- **Tuning:** `game/vr/vr_settings.tres` (`VrSettings`).

## The controllers

- **The action map** (`game/vr/openxr_action_map.tres`, written by `tools/vr_action_map.gd`, which has the bindings as tables (or edit it in the editor's OpenXR action map panel); one action set `lodestorm`): one action per gamepad element (`left_stick`, `right_stick`, `left_trigger`, `right_trigger`, `left_bumper`, `right_bumper`, the stick clicks, `a`, `b`, `x`, `y`, `dpad_*`, `view`, `menu`), on both hands, plus `aim_pose` (the pointer's ray) and `haptic` for later. Profiles: the Steam Frame (`/interaction_profiles/valve/frame_controller_valve`: a gamepad split in two), Touch and Index (grips as bumpers, Index' left A/B as X/Y and its left trackpad pressed as the menu). Without a Frame profile SteamVR would emulate a Touch controller on the Frame.
- **`VrGamepad`** reads the actions from the hand trackers each frame (also while paused) and sends them as joypad events (`Input.parse_input_event`) on its own device (15): the stick's y flipped (OpenXR's points up), a float bound to a button pressed from 0.5, an axis sent once it moved 0.01 or reached 0, everything released when it leaves the tree. So VR needs no bindings of its own: every gamepad binding of the input map and the menus' focus navigation work as they are. `tests/vr/test_vr.gd` checks that the Frame binds every action it reads and that every gamepad button and axis the input map uses can come from it.

## Pointing at menus

- **`VrPointer`** (a child of the autoload): while the local player uses a `WorldMenu`, it casts a ray from the pointing hand's controller (`VrRig.get_hand`: `XRController3D`s on the `aim` pose, which Godot names after the action `aim_pose`) and finds the spot it points at (`VrPointer.pointed_at`): on a screen (the `WorldPanel` itself, or a `Station`'s card while shown), else on the plane facing the view's camera through the menu's center (`get_view_center`), where a station's parts are. The cursor is that spot as the view's camera (`ViewCamera`) sees it (`unproject_position`), sent as mouse motion and left-button events straight into the viewport (`push_input(event, true)`: layout coordinates, so the window's stretching doesn't matter) from `VrGamepad.DEVICE`. Every menu takes them like the mouse (`WorldPanel.point` casts the view camera's ray through the cursor, which passes through the same spot; `Station._point` picks parts by screen distance), so no menu knows about VR. `PlayerAim` ignores mouse motion from that device, so pointing doesn't switch aiming to the mouse.
- **Triggers:** the pointing hand's trigger clicks (in from 0.6, out below 0.4); the other trigger hands the beam over. While pointing, `VrGamepad.mute` holds both triggers back from the gamepad.
- **The beam:** a thin unshaded box from the controller to the spot (4 m when it points at nothing) and a dot, drawn over everything (`no_depth_test`, just under the fade's render priority).

## Pitfalls

- Godot 4.7.2 names the Frame's bumper `/input/bumper/*`; Godot's development branch renames it `/input/shoulder/*`: check the action map after a Godot upgrade. A path a profile doesn't have is logged at the start ("Unsupported io path") and its action stays silent (e.g. Index' `trackpad/click`: it only has `force` and `touch`).
- The OpenXR loader logs two `xrCreateInstance failed` lines at the start with SteamVR before the instance is created; harmless.
- Godot 4.7.2 logs at every VR exit that the action map's interaction profiles leaked (one per profile), a disconnect error from `OpenXRSpatialEntityExtension` and 7 leaked textures; another VR project on the same setup does the same, and ending the session ourselves first (`uninitialize`) doesn't help. Engine-side; check again after a Godot upgrade.
- A game started outside the editor (`tools/vr.sh`) isn't seen by godot-ai's game capture; check the log (`user://logs/godot.log` or the script's output).
